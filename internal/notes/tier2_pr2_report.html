Tier 2 · PR 2 report

T2-2 · take, put_add, put with run-time int64 indices (C-102) · branch claude/tier2-sparse · 26 Sep 2026

Summary. Three new expression ops index memory with an int64 vector whose values are only known at run time, for example an entry of a pattern table chosen by a loop's step number. They are the addressing a sparse factorization needs, since its columns touch different rows at each step:

  • take(x, idx, fill=0)
  • put_add(base, idx, values)
  • put(base, idx, values)

The ops index the last axis, and leading axes are batch axes.

Out-of-range indices. An index outside [0, n) never touches memory outside the array. take reads fill instead, and a put writes into a scratch slot belonging to its own lane. So padding a ragged list with n is safe, and the writes stay unconditional.

Derivatives. All three ops are differentiable in forward mode (one seed or many), in reverse mode and to second order. Their sparsity is conservative but row-local.

Speed. A row scan that computes A x from padded CSR tables runs within 2.1× of baked-in indices, and the padding explains that gap. The transposed product, which accumulates into the carry, is O(n²) because each step copies the carry. The in-place proof in T2-3 removes that copy.

Suite: 1 113 passed, 88 skipped; the same four failures appear only in the VM. ruff, ty and the docs build are clean. Mutation checks: 13 of 13 mutants were killed, 2 of them only after adding tests that the first run showed were missing.

Index arithmetic. +, - and * between an integer expression and a Python int now stay integer, so k * width + arange needs no casts. Before this change, the Python int became a float64 constant and the operation raised a mixed-dtype error.

2. Generated code

for (j = 0; j < 4; ++j) {                      // put_add, n = 6, 4 lanes
  int64_t i = idx[j];
  int64_t d = ((0 <= i) && (i < 6)) ? i : (6 + j);   // own scratch slot per lane
  s[d] = s[d] + v[j];                           // s has 6 + 4 slots
}
for (j = 0; j < 4; ++j) {                      // take
  int64_t i = idx[j]; uint8_t in = (0 <= i) && (i < 6);
  out[j] = in ? x[in ? i : 0] : fill;           // the read address is clamped too
}

Per-lane scratch slots. If all padded lanes wrote one shared slot, each padded lane's read-modify-write would wait on the previous one through memory. The review of plan v3 measured that chain.

Batched puts. A batched put keeps its scratch slots after all rows, so the first rows × n entries keep their row-major layout. A put that is a Function output is copied out of its larger buffer.

Scalar expansion. Procedures that contain these ops are not scalar-expanded, because scalar expansion resolves every address at generation time.

3. Tests

tests/integration/test_runtime_index.py has 27 tests:

  • Values against NumPy. Rank-1 and batched bases, with five index sets: plain, repeated, padded (n, −1, 1000, −7), all out of range, and empty. Also a take from an empty axis.
  • Graph-computed indices. Indices built from integer arithmetic on an input and from a table read at run time.
  • Fusion and hoisting. A chain of put_add → put → take between elementwise code, so loop fusion and hoisting see it.
  • Derivatives.
    • A nonlinear function mixing all three ops, with a repeated and a padded lane: value, Jacobian, gradient and Hessian with respect to both inputs against finite differences, under SCALY_STRICT_JVP_MANY=1.
    • Batched forward and reverse modes agree to 1e−12, and rows do not mix.
    • A padded lane's tangent is 0 whatever the fill.
  • Sparsity. The pattern contains the true Jacobian with respect to both operands, at three index sets, and is block-diagonal by row.
  • The typical use. A row scan over a padded CSR table computes A x and Aᵀy; both match SciPy to 1e−13. Gradients with respect to the values and x match finite differences, the Hessian in x is exactly 2AᵀA, and the Hessian in y equals the closed form.
  • Generated C and validation.
    • Each padded lane addresses its own slot, with no conditional in the loop.
    • A .scalar() hint on a function that uses take leaves the function unscalarized, and its results are correct.
    • Invalid index dtype, index rank, value shape and scalar bases are rejected.

Mutation checks (13 of 13 killed):

  • no lower-bound check
  • a shared scratch slot
  • no accumulation
  • no fill
  • no row offset in a batched take
  • scalar expansion allowed
  • put's adjoint passing overwritten entries
  • take's adjoint using put
  • the fill leaking into the single-seed tangent
  • put's multi-seed tangent using put_add
  • sparsity without the values
  • sparsity without row blocks
  • Python ints not kept integer

The first run left two mutants alive: the single-seed fill and the values' sparsity. Two tests were added for them.

Missed optimizations in the generated body (T2-8). Each row still runs one loop per op: the lane indices, the two takes and the product. Index-aware fusion would merge them.

Bounds checks (T2-8). Proving that indices read from a constant table are in range would remove most of the checks.

Loop slicing. A table sliced per step by the scan itself costs a pointer offset. Reading a table with take by k * width + j costs a checked load per lane, so the docs recommend slicing.

5. Open points

  • T2-3 (next). Update the carry in place through put/put_add chains, proven at the scan node from the constant tables. The carry needs room for the lanes' scratch slots.
  • T2-8. Fuse lane loops and drop bounds checks that the tables prove unnecessary.
  • Sparsity override. The conservative row-local pattern makes a sparse Jacobian through a solver dense. custom_derivative needs a sparsity override (T2.f).
