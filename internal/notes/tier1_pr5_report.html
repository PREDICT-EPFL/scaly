New capability

x, n_iter = sc.while_loop(not_converged, newton_step, x0, max_iter=50)

This is the generated C for a Newton solve, and it is the same for any max_iter:

long long k_t0 = 0;
for (; k_t0 < 50; ++k_t0) {
  notdone_raw((s0 + ((k_t0 % 2) * 2)), s1, NULL);
  if ((!s1[0])) break;
  newton_raw((s0 + ((k_t0 % 2) * 2)), (s0 + (((k_t0 + 1) % 2) * 2)), NULL);
}
s2[0] = ((double)k_t0);                       // n_iter
res[0][c] = s0[(((k_t0 % 2) * 2) + c)];       // the final carry, copied out once
  • Contract: cond maps the carry to one bool and body maps it to the next carry. n_iter is a float64, which is exact for any count; this follows the Q4 decision.
  • Carry storage: the same ping-pong storage as scan. The final slot is known only at run time, so the carry is copied out once after the loop, not once per step.
  • Differentiable (Q3):
    • Forward mode is a while loop over [c, ċ]. Its condition reads c only, so it takes exactly the primal's steps.
    • Reverse mode is a max_iter-step backward scan over the stored carries. Steps with k ≥ n_iter pass the cotangent through unchanged via select. The stored slots past the last step hold the final carry, so the backward pass never reads uninitialised memory.
    • The step count gets a zero derivative, since it is piecewise constant.
  • Sparsity: the carry's pattern is the closure of the step pattern (at most max_iter powers, stopping when it stops growing). The step count has no pattern.
  • New program-dialect construct:
    • BREAK_IF, which the verifier only accepts inside a SERIAL loop.
    • FOR(exit_var=True), whose loop variable outlives the loop and holds the trip count.
    • unroll_unit_loops never removes such a loop. The other program passes needed no changes: scalarize already declines statements it does not know, and hoist_invariant only matches single-call loops.

Deviations and notes

  • Reverse mode through the stored carries (reverse over reverse) raises NotImplementedError. Forward over reverse, which is what sc.hessian needs, is supported.
  • The control C snapshot was not extended with a while loop. The code shape is pinned by test_while_loop_code_is_constant_in_max_iter… instead, which also checks the break and the loop variable declaration.
  • Found in passing (pre-existing, not changed): a Function whose input and output share a name, such as ["x"] → ["x"], lowers to a clobbered buffer and fails in scalarize with an unhelpful assertion. Only solver Functions are meant to share names. This should become a clear error at Function construction.
