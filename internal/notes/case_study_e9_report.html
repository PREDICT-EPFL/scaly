Case study E9 · Neural Process MPC

Branch devrush (uncommitted) · 29 Sep 2026 · code in examples/case_studies/np_mpc/ · upstream jowaibel/neural_process_mpc at 2d8de66

Summary. The Furuta swing-up of Neural Process Model Predictive Control (Waibel, Mello Rella, Jones, 2026). A conditional neural process encodes a short context trajectory into a latent z, and its decoder is the MPC's one-step model. The authors' code was built and run as published in all four of its implementations: CasADi in Python and C++, laOPT with IPOPT, and laOPT with SQP-PIQP. Each exists for the neural model and for the equation-based baseline. Scaly then reimplements the encoder, the decoder and both MPCs.

  • The reproduction runs. baseline/setup.sh pins and builds everything in 70 s. All six of the authors' C++ eval programs print OK against their Python solutions, with both IPOPT builds. One logging-only patch was needed, because the CasADi wheel's libc++ crashes the C++ clients when they print a DM.
  • Scaly poses exactly the authors' NLP. On the 100 OCPs their controller met in one swing-up, Scaly's Opti mirror takes the same IPOPT iteration count on every instance of both models, with solutions equal to 6e-16. Scaly's encoder, which uses erf for GELU, reproduces their z to 1.1e-6 (float32). All 126 adaptation episodes, delayed loop and immediate, agree in closed-loop cost to 6e-6 and settle at the same step.
  • Getting there took one finding. Opti puts constants in a row's bound or inside the row depending on which side has variables. IPOPT's bound push and relaxation scale with |bound|, so the same inequality written with its constant on the other side takes different iterates. A loader swap onto CasADi's IPOPT ruled out the build.
  • Speed, same problems and starting points. On the neural model Scaly's solve takes 3.83 ms, against 17.45 ms for the authors' controller as published (4.6×), 15.1 ms for their C++ CasADi, 8.93 ms for CasADi's jit and 36 ms for laOPT's IPOPT. Pointed at CasADi's IPOPT, Scaly's solver takes 7.73 ms. Against jit that makes the oracles and glue worth 1.16×, and the IPOPT build 2.0×.
  • The SQP is where Scaly loses. With laOPT's objective-only Hessian, laOPT's SQP converges on 94/100 neural OCPs at 1.57 ms; Scaly's converges on 88/100 at 1.25 ms. In the authors' real-time setup, the laOPT SQP client swings up in 0.2 s. Scaly's SQP client doesn't: its first solve from the hanging state takes 0.5 to 8 s. The cause is its convexification of an indefinite objective Hessian (CS-19).
  • In real time, on the authors' own server, Scaly's IPOPT client swings up in every run at 250 to 500 solves/s (neural: cost 157, upright at 0.26 s). The authors' C++ CasADi clients do not swing up on this Mac. Their solves take 20 to 45 ms on average with the wheel's IPOPT, and they apply unconverged iterates that violate the torque bound: up to 1.68 N m against 0.05.
  • The release's loop is not the paper's. The Python controller compensates a one-period delay, so its torque acts one period late. On system 3 it overshoots to 4π, costing about 320 at any context size, where the paper reports 188 at 100 steps. The same controller without the delay gets 176 to 205, near the paper's numbers.

1. The benchmark and the reproduction

  • Model. Encoder 7 → 64 → 128 → 128 → 64 → 4 (GELU) over context pairs, averaged; decoder 9 → 32 → 32 → 2 (sigmoid) for the mean velocity change, angles by the trapezoid. Checkpoint model/model.pth, the same bytes as the benchmark problem's vendored cnp_model.pth.
  • MPC. N = 12, dt = 20 ms, stage cost on 2(1 − cos θ), inter-stage cost, LQR terminal weight from the model's linearization at upright, |φ| ≤ 2 + s with a penalized slack, |τ| ≤ 0.05, the initial state as a ±1e-3 band. The equation baseline has the analytic model under implicit midpoint.
  • Built and run. The Python controller runs under its pinned environment (PyTorch 2.5.1, CasADi 3.7.0, Python 3.12), and the C++ programs build against laOPT 8f9820a (the discrete-dynamics merge they need), PIQP v0.6.2, Eigen 3.4.0 and yaml-cpp 0.8.0. The CasADi C++ SDK and "CasADi's IPOPT" (3.14.11, MUMPS 5.4.1) come from the wheel. CMake builds laOPT's IPOPT targets twice, the second time against Scaly's IPOPT 3.14.19. otool, DYLD_PRINT_LIBRARIES and a probe written into each output confirm which IPOPT each binary loads.
  • Their deploy, as published. It encodes z from a 2 s real-time context experiment, then swings up (cost 336, settled at 0.58 s, mean solve 15.8 ms). A blocking plt.show() in its parameter-estimation step needs MPLBACKEND=Agg to run headless.

2. What was built

  • scaly_impl.py. It reads the CNP with nn.load_torch_state_dict, without torch, and writes both OCPs in two forms. opti mirrors MPCController._build_optimization and laopt mirrors MultipleShootingXDiff over FurutaNPOCP/FurutaEqOCP. The dynamics and the stage cost are each one vmap; x0, z (or p) and P are runtime parameters, so one compiled solver serves every latent code. The solvers are IPOPT with the authors' settings and Scaly's SQP with laOPT's.
  • protocol.py, NumPy only and imported by both environments: the plant (analytic Furuta, explicit midpoint at 4 kHz), the context experiment, and lockstep, which reproduces run_controller over RuntimeBase step for step, including the delay compensation and the warm start's retries.
  • Harnesses. baseline/upstream.py (their controller from their classes: lockstep, grid, replay, export), run_scaly.py (the same for Scaly), baseline/replay_{laopt,casadi}.cpp (their OCP classes and configureSolver), baseline/run_realtime.py (their agents against their server), realtime_scaly.py (a client like their C++ ones), compare.py (all of it, in fresh processes, on a quiet machine).
  • np_mpc.ipynb. It runs the Scaly side live (z, 20 of their OCPs replayed with identical iterations, a closed loop matching theirs to the printed digit) and plots the recorded results.

Closed loops

  • Lockstep, system 3. Cost, settling step and ms per solve are 325.81, 28 and 17.6 ms for the authors' controller, 325.81, 28 and 3.84 ms for Scaly's Opti form, and 325.81, 28 and 2.94 ms for its laOPT form. The states agree to 7e-5; the authors' model predicts in float32. Without the delay both score 199.67 and settle at step 24.
  • Adaptation grid. Three systems, contexts of 1, 20, 50 and 100 steps, five seeds each, plus the equation baseline. The authors' and Scaly's episodes agree in cost to 6e-6 and in settling step in all 126 episodes. Mean solve 17.4 against 3.7 ms. A new z costs the authors' controller an Opti rebuild and solver construction, 38 ms; Scaly needs the Riccati solve (3 ms) and one solve (5 ms).
  • Real time. Median of three 1 s runs on their server, neural model. Their laOPT SQP client scores 202.6 and is upright at 0.20 s; Scaly's IPOPT client scores 157.1 at 0.26 s (363 solves) and its Opti form 181.8 at 0.20 s. Their CasADi C++ client and their laOPT IPOPT client fail, and their Python deploy settled within 1 s in 1 of 3 runs. On the equation model Scaly's clients score 148.9, their laOPT SQP client 158.1 and their laOPT IPOPT client 285.9.

4. What the numbers say about Scaly

  • Faithful by construction. Iteration-identical IPOPT runs make the per-solve comparison exact: the same number of the same iterations, so the time ratio is the implementation's. The loader swap splits it into IPOPT build (2.0×) and oracles plus glue (1.16× against CasADi's compiled jit). Those match the benchmark problem's controlled 2×2 in fairness.md (1.13× and about 2×).
  • Runtime parameters pay off modestly here. Opti rebuilds in 38 ms per latent code, so the adaptation advantage is about 30 ms per new z, not seconds. The larger win is the per-solve time: 4.6× against the controller as published.
  • SQP robustness. Scaly's SQP mirrors laOPT's settings but converges less often on the swing-up. Its normal-space damping escalates to 1e9·AᵀA on negative curvature that lies in the objective's own directions, followed by a diagonal shift of up to 1.8e6. PIQP then misses its limit at 50 iterations, and at 1000. With hessian="exact" it converges on 95/100. CS-19.
  • Smaller items. nn.load_torch_state_dict reads whole checkpoints but is typed as returning a flat state dict (CS-20). The benchmark problem's README still says Scaly lacks erf (CS-21). sc.dot with a constant weight vector containing zeros keeps structural Hessian entries: 191 nonzeros against CasADi's 167, harmless to the iterates.

5. Tests and checks

  • tests/integration/test_case_study_np_mpc.py, 7 tests covering three things. The GELU encoder (erf, vmap, masked mean) against NumPy and finite differences. Initial-state bands that follow a runtime parameter across consecutive solves of one generated solver, as rows and as variable bounds, under IPOPT and SQP; nothing else tested parameter-dependent bounds. And the two mirrors agreeing on a miniature OCP. Node-ID baseline updated (7 ids).
  • Mutation checks, each on a scratch copy via PYTHONPATH: IPOPT's wrapper computing bounds once, the SQP template computing bounds once, and erf emitted as erfc. All three were caught.
  • ruff format, ruff check and ty are clean on the study's scripts and the test. The notebook has the ty import diagnostics every study notebook has (CS-18). tests/integration: 425 passed.

6. Fairness notes and what was not done

  • This is not the reference machine: an M3 Max on macOS 26.6 with Apple clang 21. The upstream C++ builds at its Release flags, Scaly's JIT at -O2. Each timed process waited for load average below 6, and every replay kept the fastest of 3 fresh processes per instance.
  • Python-level timers were used for the Python columns, steady_clock around solve() for the C++ ones, and the Python call for Scaly. Scaly's C-side timer (t_total) is in results/replay.json.
  • The authors' C++ CasADi real-time result depends on the wheel IPOPT's speed on macOS. On their Linux machine the source comment implies about 4.3 ms per solve. Not rerun on Linux.
  • Not reproduced: training, the dataset generator, and the paper's real-time adaptation runs themselves. The adaptation grid runs in lockstep with NumPy's random contexts.
  • The case-studies plan has no E9 entry; this study was added on request.
