Tier 2 · PR 3 report

T2-3 · in-place carries through run-time-index updates, proven at the loop (C-103) · branch claude/tier2-sparse · 26 Sep 2026

Summary. A scan or while body whose next carry is a chain of put/put_add updates now overwrites a single carry slot. It no longer copies the carry into a second slot every step. Chains mixed with index_add/index_set qualify too.

Why the proof lives at the loop. The body cannot be proven safe on its own, because its indices are run-time values. The loop, however, knows the constant tables it slices and the step number, so it evaluates every index for all steps at once and checks that no read sees an entry already overwritten in the same step.

What this unlocks. The sparse factorization needs two patterns: reading earlier columns while writing the current one, and accumulating into a work vector. Both now run in place. A sparse forward substitution qualifies, and it matches SciPy.

  • Aᵀy by row accumulation at n = 2 000: 2 283 → 51 µs (45×).
  • At n = 20 000: 493 µs, and generation takes 0.6 s.

Suite: 1 124 passed, 88 skipped; the same four failures appear only in the VM. ruff, ty and the docs build are clean. Mutation checks: 10 of 10 killed, after two tests were added and one dead check was removed.

1. The rule

in_place_steps(body, steps) in passes/lowering.py decides whether the chain may run in place. steps[p] holds the value of body input p at every step. It is filled for inputs the loop slices from an int64 constant, which includes the step number.

  1. Chain. update_chain finds the chain u₁ … u_m rooted at the carry. This is structural only; the other steps decide safety.
  2. Write sets. Each update's indices are evaluated for all steps by _step_value, a vectorized evaluator for integer expressions. It handles constants, sliced inputs, + − ×, min/max, casts, reshape, slices, gather, take, concat and stack. An index it cannot evaluate, such as one read from the data, fails the rule. Write sets are flat positions, row by row, with dropped lanes marked −1.
  3. Read sets. The values of update i may reach a link u_j only through take, gather or a slice, possibly of a reshape. Anything else that uses a link whole fails the rule, for example a sum or an elementwise op on the carry.
  4. No overlap. At every step, the read set on u_j must be disjoint from the writes of updates j+1 … i. That includes update i itself: fusion may interleave a value's lanes with its update's lanes. The check is one sort-based intersection over (step, position) keys.
  5. Other outputs. No other output of the body may read a link.

How it combines with the old rule. The body-only rule for fixed-index chains (in_place_chain) is unchanged and is tried first. The same _inplace procedure serves every loop that proves it, because only its validity depends on the tables.

Scratch slots. A padded lane of an in-place put writes to a scratch slot of its own after the carry's entries, so the loop allocates cs + rows·lanes for the carry.

Reverse mode. Reverse mode stores every carry, so a loop whose trajectory is needed keeps its per-step slots, exactly as before.

2. Tests

tests/integration/test_in_place_runtime.py has 11 tests. Every case is built twice, with donation on and off; the results must be equal bit for bit, and the C must contain an _inplace procedure exactly when the rule should accept.

  • Sparse forward substitution Lx = b with padded row tables: it runs in place and matches spsolve_triangular to 1e−12. Its gradients with respect to the values and b match finite differences; that loop stores the trajectory and so correctly keeps its slots.
  • Accumulation with reads and writes from tables, in three variants: disjoint at every step (in place); reading the entries it writes (refused); overlapping at one step out of eight (refused). All three match NumPy.
  • Reads of the entering carry after an earlier update. Allowed while the later writes miss them, refused when an earlier update writes what is read.
  • Cases that must keep two slots:
    • a data-dependent index;
    • another output reading the carry;
    • a value reading the whole carry through a sum;
    • a value reading a fixed entry of row 1 that a column write reaches.
  • Batched carry. An index_add then a padded put_add on a batched carry runs in place, with the scratch slots after all rows.
  • while_loop(index=True) with a put body runs in place.
  • Helpers tested directly: update_chain and in_place_steps, including unknown tables and padded lanes on both sides.

Mutation checks (10 of 10 killed):

  • no overlap check
  • checking only the update's own writes
  • no check on other outputs
  • ignoring non-reader uses of a link
  • scratch sized for one row
  • flat positions without the row offset
  • keys without the step
  • integer arithmetic evaluated wrong
  • the scan-level proof not used
  • unknown indices treated as 0

The first run left three mutants alive. One was dead code: the values of update i cannot read u_i or later, because the graph is acyclic, so that check was removed. The other two now have tests: whole-link reads, and row positions in a batched carry.

Where the time goes now. The in-place transposed product is within 1.4–1.7× of the baked-in form and 3.6× of SciPy at n = 20 000. What remains is lane padding (16 lanes for an average of 6 entries), a bounds check per lane, and one loop per op. T2-8 addresses these: fusion, and bounds proven from the tables. The segment layout in T2-5 addresses the padding.

Generation cost. At n = 20 000 generation takes 0.6 s, most of it compiling the 320 000-entry index tables. The proof itself is a few vectorized NumPy passes.

4. Open points

  • Same-lane rule. A value may not read what its own update writes, even in the same lane (for example x[i] = 0.5·x[i]). Relaxing this needs a guarantee on how lanes fuse; put_add covers the scaling case.
  • Reverse mode. Loops differentiated in reverse keep every carry. For factorizations the implicit derivative (T2-7, via custom_derivative) avoids that.
