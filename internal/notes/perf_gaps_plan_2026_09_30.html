Remaining speed gaps: the implementation plan

How the proposal in perf_gaps_proposal_2026_09_30.html (items A1–A12, B1–B5, K0–K5) gets built, tier by tier, with every optimization parameterized by a description of the target processor · branch devrush, pushed at the end of each tier · started 30 Sep 2026 · Apple M3 Max, Apple clang 21, the JIT's -O2 -mcpu=native -fno-math-errno

Summary. Ten tiers, ordered by expected payoff over effort. Tier 0 adds the target descriptor, sc.Target, and moves the tuning constants already in the compiler onto it, with the generated C unchanged on the M3. Tier 1 takes the cheap kernel wins, the GEMM cliff past 64 columns and the straight-line threshold of the dense factorizations. It also takes the two measurements that decide Tiers 3 and 5. After that come the generation-time solver choices (Tier 2), the chain's instruction-cache cliff (Tier 3), and then vector rendering and register tiles (Tier 4), which the dense factorizations (Tier 5) build on. The AD op-count campaign, the solver-robustness items, the case-study AD items and the multistage backend follow.

Status: Tiers 0–4 done (C-203 … C-206, C-209 … C-213). The generated IPM, with its backend chosen automatically and timed as PIQP times itself, now takes 0.637 of PIQP's better backend's time (0.823 above 50 µs). sc.Target is in; large products no longer fall off the L1 cache; small factorizations, solves and products take the forms that measured faster on the M3; the chain's stage derivatives are split into groups that fit the instruction cache, which takes chain M = 9 from 2.41× CasADi SX's time to 1.14×; matrix products run in register tiles written as vector statements, 46–54 GF/s, within 2% of BLASFEO's time to n = 96. Tier 5 next. Each tier's section is rewritten from the previous tier's results before it starts. Its results replace its estimates when it ends.

Decisions

Taken with Colin at the start (30 Sep 2026):

  • The target enters at render time. sc.Target is a frozen description of the processor. render_c_module(fun, target=), write_module and scaly_codegen --target NAME take it. The JIT defaults to the detected host, and sc.target(t) (a context manager) and sc.set_target(t) override it, as sc.options and sc.set_options do for build-time options. Lowering and the program passes read it. Graphs stay target-free, so one graph renders for several targets. It is part of the JIT cache key.
  • Rounding may follow the target, with a flag to turn that off. A target may choose tile shapes, block sizes and lane counts that change the last bits of a result, so results can differ between targets. Target(rounding="portable") turns this off. Every choice that shapes floating-point code then takes the reference machine's (the M3's) value, so the generated C is the same for every target. The IPM's decision-trace gates (QBEACONF, QSHARE1B) run under both settings on the host.
  • devrush, one commit per item, pushed at the end of each tier. Other sessions' uncommitted files in the checkout are never staged.
  • Process: this living plan plus commits. Each item gets a todo id, differential tests, mutation checks and timings (below). At the end of each tier a review agent reads the diff before the push. There are no per-item HTML reports or tags.

Tier 0 · the target descriptor done

What was built (C-203). ir/target.py: Target, thirteen presets, host_target() from sysctl (macOS) or /proc and /sys (Linux), and the target in force (sc.target, sc.set_target, sc.get_target, SCALY_TARGET). This M3 Max is detected as exactly the apple-m3 preset. lower_function(target=) passes it to every rule as ctx.target and records it on the PROGRAM as its tuned_for attribute for the passes, which the listing leaves out. render_c_module, render_c_source, render_c_api_header, workspace_size, write_module and scaly_codegen --target take it. CModule carries it and the AOT flags for it. A Function called under another target renders again (the JIT handle records its target), and an equal target reuses the build. The O6 row blocks are now Target.row_blocks (8, 4 and 2 registers of doubles) and row_blocked_max (four of the widest). The other constants stay where they are, since each one changes rounding or generation time, and move in the tier that measures it: the reduction and mat-vec lanes (B4), the Cholesky tile (Tier 5), the scalarization budget (Tier 3).

Gates. (1) All 26 corpus kernels, including the four benchmark oracles, render byte-identical C to the base commit under the host target. (2) Full suite: host 4 499 passed after one fix. bench/harness/timing.py set _compiled by hand, and now calls _compile(). Under SCALY_TARGET=x86-64-v3 and generic, the IPM decision traces, the solver conformance suites and every numerical test pass. The seven failures were structural tests that encode the M3's widths, now pinned to apple-m3. The block-width test now runs under three targets. (3) The 26 kernels rendered for x86-64-v3 cross-compile with -target x86_64 -march=x86-64-v3. (4) ruff, ty (the touched files) and the docs build are clean. The C snapshot renders for apple-m3, so it is the same on every machine. 26 mutants, all killed.

The finding that changes the later tiers. Under the AVX2 target's widths, four corpus kernels render different C. Three of them compute the same bits. unbumpercars_8 differs by up to 5.5e-17 (relative 2.7e-14), although every output is still summed in order of k. The cause is one 256 × 6 product. The M3 blocks four columns and streams two, and the 256-bit target streams all six. Clang contracts the streamed row into fmadd, but lowers the SLP-vectorized block's llvm.fmuladd to a separate fmul.2d and fadd.2d. So any change in loop shape can change bits, through the compiler's choice to fuse or not. Consequences:

  • rounding="portable" therefore means one C for every target, not one summation order. Every derived choice goes through Target.choices, which under portable is the M3 preset. A test renders every preset under portable and gets the same source and the same bits.
  • Every later kernel change (K0's loop order, K2's tiles, K3's blocks) is a rounding change on the host, even where it keeps the order of summation. Each one needs the IPM decision-trace gates, not only the corpus timings.
  • The case for K1 is stronger. Explicit fma() calls or vector types in the generated C would make fusion a decision of the generator rather than of the compiler's vectorizer. That is reproducible across compilers and loop shapes, and it can be measured in Tier 4.

Tier 1 · cheap kernel wins and the two measurements done

Native baseline first. The proposal's kernel ratios were from gcc 11 in a Linux VM. Natively on the M3 with Apple clang, against the vendored BLASFEO (ARMV8A_APPLE_M1, panel-major), with kernels.py: GEMM is 1.2–1.5× BLASFEO at n = 16–64, 3.0–3.5× at 96–128 and 4.7× at 192–256. POTRF is 1.7–2.4× from n = 16, and TRSM 1.8–2.4× from n = 12. The VM did not show two things. GEMM at n = 8 and 12 is 2.0× and 2.9× BLASFEO, because scalar expansion turns it into straight-line code that clang does not vectorize. And every factorization and solve loses 1.3–3× the moment it becomes a loop at n = 9. Tier 1 grew one item (C-206) and widened another (C-205) to take these.

What didn't work, and why. Counting a solve's body as n² regardless of right-hand sides produced a Hessian test whose 100-seed solves became 860 KB of C, which clang took more than 10 minutes to compile. A solve's straight-line body is n² m once scalar expansion unrolls the loop over the right-hand sides, and that is what is counted now. It gives up the measured wins of straight-line solves with many right-hand sides (0.57–0.90 at 16×16 to 32×32) for bounded code. Tier 5 can revisit it with a program-wide code budget.

Review round. A review agent read the three commits and measured what it doubted. Its findings, all fixed before the push:

  • K0 divided by zero for an empty reduction next to a wide b. It now needs k > 0.
  • K0's panel copy has to be paid for by the rows that share it. The first version lost 1.25–2× on products of two or three rows. Measured by row count: a wide b pays from six rows. A b that is merely past the budget re-reads fast enough from L2 that the copy pays only for a b larger than the whole L1d, and from sixteen rows (0.91 at eight; even at 128 rows for twice the panel). Those are the triggers now (PANEL_ROWS_WIDE, PANEL_ROWS_LARGE).
  • C-205 undercounted LU. Its straight-line row swaps add about n³ selects to the 2n³/3 eliminations, and straight-line LU measured 1.4–2.3× slower from n = 14 (vmapped 400×). It is counted as 5n³/3 now, straight-line to order 13 on the M3.
  • C-206 kept products with a constant operand in loops, where scalar expansion would fold the constant's zeros and ones. Forward-mode Jacobian seeds, selection and kinematic matrices went 2.9–4.8× slower. A constant operand now leaves the product to expansion.

Seven more mutants, all killed after two tests were added. Full suite after the fixes: 4 590 passed.

Tier 3 · the chain's stage derivatives in groups that fit the instruction cache done

What was built (C-211). Forward mode across a mapped call builds one tangent body for all of a formal's seeds, and at chain M = 9 that body was 339 KiB of code. ad.forward._seed_groups now estimates an expanded body's code from its graph before it is lowered (_body_ops: arithmetic nodes by size, a product by its multiply-adds, at BYTES_PER_BODY_OP = 5; the chain's stage bodies measured 3.9–5.4 bytes per counted operation at M = 3–9). Past Target.body_bytes, half of L1i and through choices, the seeds are split into contiguous groups. Each group is its own mapped call over every trip, with the other seeds' constants zeroed, and the groups are joined along the seed axis into the layout the single body gave. All four paths do it: periodic constant seeds (the sparse Hessian's star colours), local colours (the dense Jacobian), the structured sparse Jacobian, and runtime seeds. _pack_jvp_maps does not pack the groups back into one body. Only a body expanded into scalar code is split: one whose callee asks for it (.scalar(), as the chain's stage does, inherited by its derivatives) and that has no run-time index. A body kept in loops stays compact at any size. The choice is made while the graph is built, the one exception to Tier 0's render-time rule, and scaly_codegen --target imports the module under the target it names.

The rule that came out of measuring it. The first version split a body into ⌈body / budget⌉ groups. Counting the work each budget generates showed the flaw: every group recomputes the primal and the adjoint, 2 477 of M = 9's 88 175 operations. On x86-64-v3's 16 KiB budget, M = 9 was cut into 27 groups for 52% more work, and every group's body still missed the budget (29.5 KB), because the shared part alone is about 9 KB. The count now divides only the tangents, by the budget left after the shared part (estimated as the callee's own body: 1 205 and 2 477 operations at M = 5 and 9, against the 1 406 and about 1 776 the grouped bodies imply). A formal split into groups also stops sharing the primal with the other formals' packed body, so a split into count groups is charged count recomputations. The seeds stay in one body when the shared part alone is past the budget, when groups of one seed would not fit either, or when that charge would add more than half the work (MAX_RECOMPUTE). A split within that cap pays wherever the cost per operation rises by 1.5× or more past the instruction cache; the M3 measured 2.8× and the VM 2×. On the M3 the rule makes the same groups as the first version (2, 3 and 5 at M = 5, 7 and 9). On x86-64-v3 and the Cortex-A53 (32 KiB) the chain stays one body at every M. On the 64 KiB Neoverse V2 and Cortex-A76, M = 5 and 7 are split into 5 and 10 groups and M = 9 stays whole, its recomputation past the cap. x86 could not be timed here, so the cap errs toward the code it had before.

Tier 4 · vector types and register tiles for the products done

Revised after Tier 3 and a prototype. Natively after K0, GEMM is 1.2–1.5× BLASFEO at n = 16–64 and 1.67–1.89× at 80–256 (30–33 GF/s). The assembly shows why: per step of k, the O6 row block issues one scalar load of a and eight vector loads of b for eight fmla.2d. That is bound by the loads, at about 2.7 of the M3's four FMAs a cycle, which is its 52–62% of peak. Clang already fuses each multiply-add there; Tier 0's separate fmul and fadd were in a narrow block only.

The prototype (a scratch copy of the lowering, results/kernels_t4_proto_4x8.json and shapes_t4_proto_small.json): four rows at a time, eight columns per tile, sixteen vector accumulators, still scalar C with private sums. Where clang's SLP vectorizer takes the tile it issues eight loads per sixteen FMAs and is bound by the FMAs. GEMM at n = 16–64 ran at 51–54 GF/s, 0.86–1.04× BLASFEO's time (0.63–0.72 of today's), with every output bit for bit today's, since each is still one chain in order of k. A single block of four rows gained as much: 4 × 64 × 8 took 0.44 of today's time. But the vectorizer's cost model declined other tiles ("possible but not beneficial with cost 0 >= 0"): at 8 × 8 × 8, 8 × 32 × 8 and 12 × 12 × 12 the tile stayed scalar and spilled, 2–2.5× slower than today. The same 8 × 8 × 8 tile written with GNU vector types compiles to sixteen fmla.2d with no spills. And n = 96–128 did not change, because K0's panel passes still run one row at a time.

  • C-212, K1 for the products. A tile's columns become an inner range of kind VECTOR (the kind exists and nothing uses it yet), Target.vector_doubles lanes wide, whose body the renderer emits as GNU vector statements. An access of unit stride in the range is a load or store through the unaligned, may_alias vector type the renderer already declares for STORE_PAIR (double2, widened to the target's lanes); one the range does not index is a splat; private sums indexed by it are vector variables; each multiply-add is one expression, which clang and gcc both fuse. Vectorization is then the generator's decision, not a cost model's. generic keeps scalar C, the choice for a compiler without the extensions. Per-ISA intrinsics are ruled out by how the other targets are tested: their C is compiled and run on this Mac.
  • C-213, K2. Tiles of mr rows by nr columns in the row-blocked products and in K0's panel passes. The tile comes from the BLIS analytical model: accumulators mr nr / lanes at least FMA units × FMA latency, and accumulators plus operands within the vector registers. Three fields join Target, each read by this choice: vector_registers, fma_units, fma_latency. On the M3 that gives 4 × 8, the prototype's tile. a is not packed: its mr scalars a step are what keep the tile bound by FMAs, as measured. Leftover rows and columns take narrower tiles, down to today's single row. Mat-vec (MATVEC_ROWS, MATVEC_LANES) moves onto the same fields.
  • Revisit. The thresholds set against today's kernels: C-206's middle block (the prototype's single four-row block beat today's from 4 × 8 × 8), C-205's straight-line budget, K0's panel triggers, and the IPM cost model's weights, refit if faster products change its choices on the 55 problems.
  • Gates. GEMM ≤ 1.05× BLASFEO's time at n = 16–128, natively on the M3 (kernels.py), and no small shape of the prototype's sweep slower than today. Outputs bit for bit today's on the host (each output keeps its order of k), so the IPM traces and the corpus's expected values hold. The x86 presets' C correct when run here and cross-compiling, their tiles analytical and untimed. Corpus kernels no slower.

What was built. C-212: a block's running sums are private buffers of the target's lanes, each updated in a loop of kind VECTOR (the kind existed, unused), which codegen/c.py writes as GNU vector statements when the body is float64 arithmetic whose accesses move 0 or 1 elements a lane, and as the loop it also is otherwise. The lanes are independent by the kind's contract, and a body storing a buffer it reads at another index falls back. C-213: Target.product_tile from the BLIS model and three new fields, vector_registers, fma_units, fma_latency; tiles of four rows in the row-blocked products and in K0's panels, the rows left over in one-row tiles.

C-216: what was built. Where A or G has dense rows, the condensed matrix takes Aᵀ A / δ or Gᵀ W G as a dense product on the register tiles, and P's stored triangle goes straight into the lower one, which is all the Cholesky reads. The rule (kkt.dense_rows) compares the two forms' work: the sparse form multiplies every pair of entries of a row, at about four times a dense multiply-add (PRIMALC2's seven dense rows of 231: 163 µs against 43), so a matrix goes dense from a quarter of rows × n². Two floors came from measuring: under eight columns there is no whole tile (DUALC2, seven columns, 1.08× slower dense), and under 4 096 products the dense form's copies do not pay (LOTSCHD, 532 products, 1.18× slower). A problem without such rows renders the C it did: the first version also sent sparse problems' P through the lower triangle alone, and QISRAEL, ex_svm and QADLITTL ran 2–5% slower.

C-217: what the profile said, and what was built. B3 was written as fusion of the step's loops. A profile by loop (step_lines.py, new, on DUALC8) showed something cheaper first. The step is flat: 213 loops, none above 5.4% of it, and its products with G are already fast (1.1–1.7 µs of its 12; the dense forms measured no better). But 47% of its samples sat in loops clang had left scalar, all of one kind: a select around a load, mask[i] ? 1 / x[i] : 0, the step-length ratios, flag ? a[i] : b[i]. C evaluates only the taken branch, so the compiler may not move the other branch's loads ahead of the condition; it keeps a branch per element and gives up on the loop. A graph evaluates every operand anyway. So, for a statement in a loop, the scalar scheduler (passes/program/scheduling.py) now names a select's branches, and the right operand of && and ||, in temporaries before the statement when they hold a load. What could fault or cost where C would have skipped it stays under its condition: a libm call, an integer division or remainder, a float converted to an integer. Straight-line code keeps its branches (the smallest problems ran 3–6% slower with their divisions computed ahead, within that harness's noise but with nothing to gain).

C-217's results. Isolated from C on the M3: a masked product 2.6× faster, a masked reciprocal 1.9×, a step-length ratio 1.7×, a mask && comparison 1.6×. Naming only the loads does nothing (clang sinks them back); the whole branch must be a value. DUALC8's step: 82% of its samples in vectorized loops, from 48% (step_lines_dualc8.txt). The dense IPM (ipm_dense_c217.md): DUALC1/2/5/8 0.92, 0.90, 0.93, 0.89 of their time, 0.98, 0.94, 0.72, 0.97× PIQP's dense backend: the gate is met; QPCBLEND and QADLITTL 0.92–0.93, HS118 0.94; all 55 at 0.982 of C-216's time, 0.686 of PIQP's and 0.874 over the 40 above 50 µs; nothing slower beyond the harness's noise (largest 1.012). Statuses and iterations are unchanged: the same arithmetic in the same order. The codegen corpus: only its four IPM kernels render other C (HS118 dense 0.92, QAFIRO sparse 0.92, the sparse MPC 0.98), so the sparse backend gains too. 20 mutants of the rule and its wiring, all killed.

What is left of B3. Fusion proper: one pass per intermediate vector remains, and each is now a vectorized loop of 1–5% of the step. Filed as C-219 with the profile; no problem of the 55 is step-dominated and behind PIQP any more, so it waits for one that is.
