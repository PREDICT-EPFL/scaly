New capability

# x solves x**3 + x = p (a Newton while_loop inside `solve`); dx/dp = 1 / (3x^2 + 1)
rule  = sc.Function._from_exprs("implicit", [p, x, xbar], [xbar / (3*x*x + 1)], ["p", "x", "xbar"], ["pbar"])
solve = sc.custom_derivative(solve, vjp=rule)     # jvp=... likewise; either may be omitted
  • Replacing the body's derivative: the forward rule takes (*inputs, *tangents) and returns one tangent per output. The reverse rule takes (*inputs, *outputs, *cotangents) and returns input cotangents. Because it receives the call's own outputs, the implicit rule reuses the solution rather than solving again.
  • Where it is honored: every derivative path uses the rules: forward mode at CALL and VMAP; the multi-seed forward mode behind sc.jacobian, through its per-seed path; reverse mode at CALL and inside the per-iteration adjoint of VMAP; and everything built on these, such as gradients, Hessians and sparse Jacobians.
  • Missing direction: a direction that is not given differentiates the body as before. Sparsity patterns still come from the body.
  • Solver Functions: the copy keeps a solver Function's descriptor, so the same mechanism can later attach implicit sensitivities to the vendored QP and NLP solvers.

  • With the implicit rule, the gradient costs about the same as the value: one extra division per entry. It is also exact at the solution, whereas the derivative through the steps is not.
  • Finding: at n = 1000 the implicit-rule gradient takes 2.4 s to build, against 0.3 s for the other variants. The run time is fine. The likely cause is that the auto policy scalarizes the 1000-entry rule procedure into straight-line code, and compiling it is slow. It's worth tightening scalarize's budget on elementwise procedures.

Deviations and notes

  • A sparsity= override for the rules was in the plan as an option. It is not added. The body's pattern is always a sound superset, and there is no caller for an override yet.
  • The forward rule receives only inputs, as the plan specified, so an implicit forward rule has to call the solver itself, as the test does. It could also take the outputs, symmetric with the reverse rule; that is a one-line change if you prefer it.
