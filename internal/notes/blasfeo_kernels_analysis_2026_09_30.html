BLASFEO-class kernels in Scaly

Analysis and measurement, 2026-09-30. Scripts and raw numbers: internal/notes/perf_2026_09_30_blasfeo/. Related: C-79, C-8, C-117, A7 (perf_gaps_proposal_2026_09_30.html), Tier 5 and Tier 6 (piqp_plan.md).

Verdict.

  • Can it be done? Yes. Nothing in BLASFEO depends on hand-written assembly as such. It depends on four things: a register tile sized to the FMA pipeline, a storage layout that makes the tile's operand loads contiguous, fused factorization kernels, and a reciprocal-diagonal trick. All four can be expressed in Scaly's program dialect and rendered as C with vector types or intrinsics. Scaly also has the advantage BLASFEO lacks: every size is known at generation time.
  • Competitive? On isolated kernels, parity with BLASFEO for n ≥ 32 is a realistic target, but BLASFEO's GEMM already runs at about 90% of peak there, so there is little room to beat it. For n ≲ 32, and for fused sequences such as a Riccati step, a Kalman update or a KKT factorization, Scaly should beat it. BLASFEO's Cholesky runs at only 19–36% of peak for n = 16–32, and it cannot fuse across calls or exploit structural zeros inside blocks. Scaly already beats it for n ≤ 8. On Apple M4-class chips, SME outer products are a hardware path BLASFEO does not target at all.
  • Impact. The impact is large for solvers dominated by dense blocks: the dense IPM (where Cholesky is 80–90% of a step), Riccati and multistage solvers (Tier 5, the HPIPM/Fatrop class), and estimators. It is roughly zero for AD-dominated function evaluation (chain, race cars); those gaps are C-77 and A1–A3, not BLAS.
  • Complexity. Moderate, and most of it is infrastructure already planned: C-79 vector rendering, a Tier-6 target description, and a layout attribute. The kernel generator itself is a few thousand lines of Python templates, against BLASFEO's ~128 k lines of ARMv8 and ~210 k lines of AVX2 kernel source. The effort is roughly 2–3 person-months to parity on GEMM, SYRK, POTRF and TRSM for NEON and AVX2. This is an estimate, not a measurement.

1. What BLASFEO does

  • Target regime. BLASFEO targets matrices of order about 4–300, where MKL and OpenBLAS lose to packing and dispatch overhead. Its aim is near-peak throughput from n ≈ 50 upward without cache blocking, on the assumption that the working set lives in L1 or L2 [1].
  • Panel-major storage (blasfeo_dmat). Rows are grouped into panels of height ps, which is 4 doubles on both ARMV8A_APPLE_M1 and Haswell. Storage is column-major within each panel, and the matrix is padded to a multiple of ps. The matrix is therefore already in the packed format a GEMM micro-kernel wants: the four rows of a panel at column k form one contiguous 32 B load, and no call ever packs. The BLAS API added later packs on the fly for column-major data [2].
  • Register-blocked micro-kernels in assembly, one set per ISA. Double-precision tiles are 8×4 and 4×4 on Apple M1 and 12×4, 8×4 and 4×4 on Haswell. The k loop does rank-1 outer-product updates with software pipelining and prefetch. Kernels are built from "inner" subroutines (inner_kernel_*, inner_scale_*, inner_store_*) that pass accumulators in registers. _vs variants handle ragged edges with masked stores. The vendored ARMv8 set exports about 240 double-precision kernel entry points.
  • Fused LAPACK-level kernels. Cholesky is dsyrk+dpotrf on a panel: the panel is updated by the outer-product kernel, then its diagonal block is factorized and the rows below it are solved while still in registers. Triangular solves multiply by a stored inverse diagonal instead of dividing. This fusion is why its POTRF approaches GEMM speed at moderate n.
  • Compile-time targets. Targets are chosen at build time (TARGET=X64_INTEL_SKYLAKE_X | X64_INTEL_HASWELL | … | ARMV8A_APPLE_M1 | ARMV8A_ARM_CORTEX_A76 | … | GENERIC). blasfeo_block_size.h records per target the panel size, the maximum kernel size, the cache sizes and the blocking parameters. There is no autotuning; the parameters are hand-chosen per microarchitecture, which is essentially the analytical recipe of BLIS [3].
  • No compile-time sizes. Every call dispatches on (m, n, k) at run time. It never unrolls the k loop for a known k, never exploits zeros inside a block, and never fuses across calls. HPIPM gets some of that fusion by hand-picking fused kernels.

2. Where Scaly stands today (M3 Max, Linux VM, gcc 11.4)

The comparison uses Scaly's JIT defaults (-O2 -ftree-vectorize -mcpu=native) against BLASFEO ARMV8A_APPLE_M1 on data already in panel-major format, taking the minimum of 9 samples of ≥ 20 ms each. Measured peak is 58 GFLOP/s (16 flop/cycle at 3.6 GHz). The ratio is Scaly time divided by BLASFEO time, so values above 1 mean Scaly is slower. Results agree to ≤ 2e-15. -O3 is within ±5%.

Diagnosis

  • n ≤ 8 (≤ 12 for GEMM): Scaly wins. The code is straight-line, and BLASFEO's dispatch, edge handling and loop overhead dominate at these sizes. This is evidence that compile-time sizes are worth a lot at small n.
  • GEMM at n = 16–64 runs at 52–62% of peak. The O6 tile is one output row by 16 columns. That costs one broadcast plus 8 vector loads per 8 vector FMAs, about 1.1 loads per FMA, against 0.375 for BLASFEO's 8×4 tile. It is load-bound, and 8 accumulator chains are also below the ~16 needed to keep four FMA pipes busy (assuming the ~4-cycle FMA latency of recent Apple cores).
  • GEMM at n ≥ 96 hits a cliff. COLUMN_BLOCKED_MAX = 64 sends wider rows to a triple loop that accumulates in memory, which runs at 12 GF/s. This is a trivial fix.
  • POTRF is the largest gap. The C-136 Crout is an inner-product formulation: 4×4 tiles of dot products that end in horizontal reductions, plus a division per column. BLASFEO's version is an outer-product panel update feeding a factorization done in registers with a reciprocal diagonal.
  • No explicit SIMD. Scaly emits no explicit SIMD, apart from paired stores. RangeKind.VECTOR exists in the IR but is never rendered, and the O6 report found clang spilling on the two-lane Cholesky tile. Autovectorization will not get there.

3. What processor-specific generation in Scaly would look like

The kernel layer belongs below AD and inside the program dialect. cholesky, matmul and solve_triangular keep their expression-level definitions and derivative rules, and only their lowerings change. Derivatives therefore land on the same fast kernels at no extra cost, and the generic path stays the reference.

  1. Target descriptor (the Tier 6 item). It records ISA, vector width in doubles, register count, FMA pipes × latency, load ports, whether an FMA by lane exists (NEON fmla v, v, v.d[i]), masking (SVE, AVX-512), SME tile geometry, and L1/L2 sizes. For the host it is filled from compiler macros and -mcpu=native. For cross-targets it is given explicitly (e.g. Cortex-A53/A76/A78AE, Zen 4, Cortex-M7 in single precision). It becomes part of the JIT cache key.
  2. Vector rendering (C-79's infrastructure). RangeKind.VECTOR is rendered as GNU vector_size types, plus a thin per-ISA shim for the few operations the compiler will not infer: broadcast-by-lane FMA, ld1r/vbroadcastsd, and aligned loads. Workspace gets 64 B alignment.
  3. Layout as a compilation decision. Buffers get a layout attribute: row-major, column-major or panel-major(ps), with padding. The ABI stays row-major, and internal buffers (KKT blocks, Riccati P, factors) are allocated directly in the kernel's preferred layout. BLASFEO makes the user manage dmats; Scaly can plan this globally and pack only where a buffer crosses the ABI. A cheaper first step lets each op pack locally into workspace. That costs O(n²) against O(n³) work, which is negligible from n ≈ 16.
  4. Micro-kernel templates. About six parametrized loop nests: GEMM mr×nr (nn/nt/tn), SYRK-lower, a fused SYRK+POTRF diagonal tile, GEMM+TRSM with the inverse diagonal, GEMV, and an LDLᵀ variant. mr and nr come from the analytical constraints of [3]: mrnr/Nvec ≥ Nfma·Lfma, subject to the register budget. On M-series NEON this gives 8×4, as BLASFEO chose. Sizes are fixed, so every tile is exact, edges are peeled at generation time with smaller tiles, and short k loops are fully unrolled. No _vs kernels and no run-time dispatch are needed.
  5. Macro algorithms written once in Python. Blocked left-looking Cholesky and LDLᵀ, TRSM, SYRK, and a Riccati step, written as loops over tiles. This is the "programmatic" direction, and A7 is its first instance.
  6. Selection. Choose between straight-line code (n ≲ 8–12), scalar tiles, vector tiles, and SIMD across a mapped axis (tiny blocks × many stages or scenarios, via C-79 lanes). An analytical cost model makes the default choice; an optional measured tune at JIT time is cached per (op, shape, target).

Where Scaly can beat BLASFEO, not just match it

  • Small and medium sizes. Exact tiling and unrolling with no dispatch. BLASFEO's POTRF is at 11 GF/s at n = 16 and 21 at n = 32, far from the ~50 its GEMM reaches, so this is where MPC sizes (nx+nu ≈ 10–40) live.
  • Fusion across calls. A Riccati step (Aᵀ P A, Bᵀ P B, a Cholesky of R + Bᵀ P B, a solve, and a rank update) can keep blocks in registers or L1, with no intermediate stores or calls.
  • Structure inside blocks. Structural zeros, identity blocks, diagonal Q and R, and symmetric operands. Scaly already knows the sparsity pattern; BLASFEO treats every block as dense.
  • Batching. For blocks of order 8 or less across N stages, vectorizing across stages beats vectorizing within the matrix. BLASFEO has no batched path.
  • SME on M4-class Apple silicon. Remke and Breuer measured 503 GFLOP/s FP64 with SME outer products, against 56 with Neon, using a LIBXSMM JIT generator [6]. Streaming-mode entry and exit and the latency are costly for tiny n, so this is a medium-n (≳ 32) path that a target-aware generator can choose and BLASFEO cannot. The VM does not expose SME, so it must be measured natively on macOS.

Cheap baseline. BLASFEO is already vendored in scaly-piqp, and function/extern.py can inject C with build requirements. An extern BLASFEO path would take about a week and would give BLASFEO speed at n ≥ 12. It gives up the n ≤ 8 wins, fusion, structure and SME, and it breaks the generated-code-only decision. It is better used as the gate reference than as the product.

Risks

  • Compiler quality. gcc 11 on aarch64 and register spills in intrinsics code; the O6 report already found spilling. Mitigations: explicit vector types (not autovectorization), recommending clang, and inline assembly for the innermost tile only as a last resort.
  • Summation order changes rounding. C-136 showed QSHARE1B is sensitive to pivot noise. Blocked kernels change the order again, so the decision-trace gates need tolerance rules rather than bit-exactness.
  • Scope creep into a general BLAS. Keep the set to what the solvers call, at sizes the solvers use.
  • Measurement portability. The VM clock is 3.6 GHz against a 4.05 GHz boost. Repeat natively on macOS with Apple clang, and on the x86 reference machine against the X64_INTEL_HASWELL/SKYLAKE_X kernels.
  • Hardware-tracking burden. This is lower than BLASFEO's because the parameters are derived, not hand-coded, but each new ISA still needs a shim and validation hardware.
