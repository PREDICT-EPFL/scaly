TinyMPC in Scaly · benchmark report

examples/tinympc · the three problem families of the TinyMPC microcontroller benchmarks · 52 instances · gcc (Ubuntu 11.4.0-1ubuntu1~22.04.3) 11.4.0 on aarch64 (Linux-6.8.0-138-generic-aarch64-with-glibc2.35) · 26 Sep 2026

Summary. TinyMPC’s ADMM is written once in Python (examples/tinympc/solver.py, under 300 lines with its comments) and Scaly generates C specialized to each problem. On every instance of the three published sweeps it replays the TinyMPC library’s solve call for call:

  • Same iterates. Identical ADMM iteration counts at every MPC step of every instance (all 52, at -O3 and -O2); applied inputs agree to 3e-13 on the QPs and to 2e-05 on the rocket (the library computes part of its cone projection in float; with that made double the difference falls to 9e-14).
  • Solve time (same compiler, same flags, -O3): geometric-mean speed-up over the library of 1.38× on the random QP-MPC sweeps, 2.79× on the safety filter and 2.66× on the rocket landing (at -O2: 1.07×, 2.17×, 2.34×). Slower on 5 of 52: the random QP-MPC with 16–32 inputs, down to 0.80×.
  • Code size. The generated solver is 4.4–62.9 KiB of object code (.text, constants included) against 200 KiB for the library’s three objects (40 KiB for admm.o alone), with no heap, no Eigen and no C++ runtime.
  • Compile time. 0.13–4.97 s per instance for Python generation plus gcc -c, against 7.6 s to compile the library (once for all problems, since its sizes are run-time values).

Found on the way: a Scaly lowering bug that returns wrong numbers when an output is named like an input (todo, below); the cost of the while-loop carrying its loop invariants (C-112); and five places where the library departs from textbook ADMM, all reproduced so that the iterates compare.

2. Method

  • Library: TinyMPC 023f36bd5b (main, 2 Sep 2026), built from source; one patch, the std::cout that solve prints on convergence, removed because it would be timed. Adaptive rho off.
  • Problems: mcu-solver-benchmarks dfa77a5c86: random QP-MPC (published npz data; sweeps nx 4–32, nu 4–32, N 4–50), safety filter (double integrator; nx 2–32 at N = 10, N 4–100 at nx = 10), rocket landing with thrust cone (N 2–256).
  • Same numbers on both sides. The library is set up on each instance, and its Riccati cache is written out and built into the generated solver. The closed loop runs once in Python with the generated solver; each C driver then replays the recorded sequence of warm-started solves, so both solve exactly the same problems.
  • Timing: only the solve call, clock_gettime; 5 runs of each episode from a zero workspace; the median episode total divided by the steps. Bounds are run-time inputs on both sides.
  • Build: both sides with -O3 -mcpu=native -fno-math-errno (and -O2), Eigen with -DNDEBUG. Sizes from size on the objects; compile times best of three.
  • Caveats: the machine is an Apple-silicon Mac through a Linux VM (4 cores), not a microcontroller, and both sides run in double precision; the microcontroller builds of TinyMPC use float, which this comparison does not cover.

4. Reading the numbers

  • Where the generated code wins. The stage steps are matrix–vector products with constant matrices. Scaly expands small ones into straight-line code with the entries as literals, so zeros cost nothing: the double integrator’s A, B, K and Quu⁻¹ are block-structured, and the safety filter gains grow with the dimension (5.8× at nx = 32). With fixed sizes the loops over the horizon have no bookkeeping, and the library’s dynamic Eigen matrices are gone, and so are the copies of vnew and znew the library makes at every iteration for adaptive rho, even with it off.
  • Where it loses. The random QP-MPC with 16–32 inputs converges in 4–7 iterations per solve, and each iteration is dominated by dense 16–32-wide products (Quu⁻¹, Kᵀ). Eigen’s vectorized kernels beat the scalar sums of the expanded code there (C-117), and the per-solve cost of packing the carry weighs more with so few iterations.
  • The carry. A while_loop body reads only its carry, so the references’ linear cost and the bounds travel in it and are copied at every iteration, and every field is computed into scratch and copied into the next carry. Making the bounds constants (--fixed-bounds) removes two thirds of the invariants and 2–6 % of the solve time (2.73 → 2.63 ms at nx = 32, 18.4 → 17.9 µs at nu = 32). Loop-invariant inputs (C-112, in progress on the Tier 3 branch) and writing concatenated parts straight into the next carry would remove the rest.
  • Code size and compile time are not monotone in the problem size: below Scaly’s automatic expansion limits a whole stage step (for small problems the whole iteration) becomes straight-line code, above them it stays a loop. That gives the 40–65 KiB peaks at nx = 4, nx = 32 and nu = 32 and the 2–5 s compiles at nu ≥ 24; lowering="block" keeps loops (35 KiB, 0.3 s at nu = 32) at some cost in speed.
  • Iteration counts are those of today’s library, which reorders the ADMM steps relative to the version that produced the published sheets (the published sheet has 18 iterations per solve for the safety filter at nx = 4, N = 10; today’s library takes 232 on average, and so does the generated code).

5. What the port reproduces from the library

  • The linear cost uses (Q + ρI)·xref, because work->Q stores the penalized diagonal: a bias towards the reference that textbook ADMM does not have.
  • One ρ is folded into the Riccati cache however many constraint sets act on a variable (box and cone on the rocket’s thrust), so the primal step is not the exact minimizer of the augmented Lagrangian there.
  • project_soc takes float mu and a float norm, and it projects in the metric that scales the cone axis by μ (Euclidean only for μ = 1).
  • Termination looks at the box slacks only, so cone residuals are not tested (the applied thrust can leave the cone by up to 0.09 at tolerance 1e-2).
  • tiny_api.hpp names the arguments of tiny_set_cone_constraints input-first while the definition takes the state cones first; the library’s own rocket example passes them the wrong way round (with the cones then disabled by default).

6. Scaly issues found

  • Wrong numbers: when a Function has an output named like one of its inputs, the generated C reads that input from the output buffer (LowerCtx.register_outputs overwrites self.buffers[name] in passes/lowering.py). A four-line reproduction is in the todo item. The TinyMPC solver avoids it by naming its output state_next.
  • Loop invariants in the while_loop carry (C-112), measured above.
  • Dense constant matrix–vector products in expanded code are scalar sums; a double2 form (C-117) would close the gap at nu ≥ 16.

7. Reproduce

uv run examples/tinympc/benchmark/run_benchmark.py --workdir /tmp/tinympc-bench (add --opt=-O2, --budget 150 to run in pieces, --quick for a toolchain check), then uv run examples/tinympc/benchmark/report.py. It clones the pinned TinyMPC and benchmark commits and needs gcc, g++ and size.
