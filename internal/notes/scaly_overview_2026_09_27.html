Big-picture highlights

The unifying principle is one deployment path: generated code only. Every capability below compiles to plain C with no BLAS, LAPACK or sparse library behind it, and loops stay loops rather than being unrolled into straight-line code.

Tier 1

Differentiable control flow in generated C

sc.scan and sc.while_loop lower to single C loops with a ping-pong carry, and are differentiable in forward mode (all seeds in one tangent loop) and reverse mode (stored trajectory, one backward scan per scan). A scan builds about 270× faster than the unrolled graph.

Tier 1–2

Logic, nonsmooth ops and run-time indexing

Comparisons, where, tie-aware maximum/abs derivatives, segment reductions, accumulating scatter, take/put/put_add with run-time int64 indices, ragged loops and custom derivatives. Loop carries updated through these ops are proven safe to update in place.

Tier 2

Sparse and dense linear algebra as Scaly values

SparseMatrix (static CSC pattern, Expr values), symbolic analysis with orderings, and a quasi-definite SparseLDL within 1.04–1.5× of a QDLDL-class C factorization (4–5× faster when unrolled on small KKT systems). Solves carry implicit derivatives to second order.

Tier 3

PIQP as generated code

scaly.solvers.ipm.Solver generates PIQP 0.6.2 end to end, with dense and sparse KKT backends. Status parity on 62/62 gate problems and identical decision traces on 48/48 (sparse). The sparse backend runs at 1.26× PIQP's warmed solve time, and 0.81× its setup plus solve.

Examples

Whole algorithms as one C function

iLQR, TinyMPC's ADMM, Newton with continuation, an EKF for identification and more are written in Scaly and emitted as single C functions. The TinyMPC port takes identical iterations to the library, runs 1.4–2.8× faster (geometric mean) and has a fraction of its code size.

Validation

Against CasADi, and reviewed tier by tier

17 of CasADi's own examples ported side by side: all agree, and Scaly runs 2–21× faster than interpreted CasADi on OCPs. Each tier closed with a multi-agent review; every confirmed defect has a regression test. The suite grew from 1 057 to 2 218 passing tests.

Where this sits in the plan

The work follows a six-tier plan whose end goal is PIQP as a drop-in backend="scaly". Two decisions shaped it: general sparse linear algebra comes before multistage structure, and Tier 2 is general-purpose infrastructure rather than a PIQP-private component, so PIQP is only its first consumer.

Tier 1Core IR primitives: loops, logic, indexing, custom derivativesdone
Tier 2Sparse and dense linear algebradone
Tier 3Generic primal–dual IPM (PIQP 0.6.2)done
Tier 4Drop-in backend, parity, sensitivitiesnext
Tier 5Multistage / Riccati structure, supernodeslater
Tier 6Target selection, optional external kernelslater

Each tier has quantitative gates and a kill criterion, every PR ships a report (capability, tests with mutation checks, benchmarks), and each tier ends with an agent review round.

Tier 1 · Core IR primitives

Tier 1 added the control flow and nonsmooth operations that an optimisation solver needs, all differentiable and all lowered to generated C. Scope decisions: one generated solver per fixed sparsity structure; scatter accumulates on repeated indices; nonsmooth tie conventions are a global option (default "split"); booleans and counters cross the ABI as doubles; reverse mode through loops stores the carry trajectory.

Review round and optimizations

  • Correctness fixes: a silently wrong Jacobian from interned tangent-symbol names; tangent mix-ups between inlined calls; K² code growth for K calls of a loop Function; a forward-over-forward crash; int64 inputs to callees read as raw doubles; generated C that depended on PYTHONHASHSEED.
  • Optimizations: per-step Jacobian tangents (seeds @ J); one backward scan per scan and one reverse sweep per call (C-91); division-free, composed index maps for gathers and scatters; raw-address JIT entry.
  • Result: MPC Hessian 109 → 58 µs and RK4 Hessian 1 079 → 93 µs relative to PR 8 (11.6×). A dedicated suite of 88 multi-seed loop cases; each regression test was shown to fail with its fix reverted.

Tier 2 · Sparse and dense linear algebra

Tier 2 makes sparse matrices and factorizations first-class, reusable Scaly values for Newton/SQP KKT steps, Kalman updates, implicit integrators and PIQP. All of it is generated code: the symbolic work happens in NumPy at generation time and the numeric work is emitted as loops over constant index tables.

Compiler support

  • Loop bodies can read the step number (index=True).
  • take, put, put_add with run-time int64 indices; out-of-range lanes read a fill value or write a scratch slot.
  • In-place loop carries through these ops, proven at the loop from its index tables.
  • ragged_add/ragged_dot: inner loops of run-time length.
  • custom_derivative(sparsity=) and a trajectory-memory guard.

Linear algebra (scaly.linalg)

  • SparseMatrix: static CSC pattern with Expr values; algebra, block/KKT assembly, results of sparse_jacobian/sparse_hessian.
  • analyze: natural, RCM, MMD and auto orderings, elimination tree, pattern of L, segments chosen by dynamic programming.
  • SparseLDL: quasi-definite LDLᵀ without pivoting; "scan" or "unroll" schedule; solve(b, refine=k); inertia() and health().
  • Dense cholesky, ldl, solve_triangular, cho_solve, ldl_solve, solve.

Review round

Five agents found ten defects, six of them silent wrong numbers (for example generated names shadowing inputs, -0.0 in tables, NaN second derivatives of x**p at 0, put's reverse rule with repeated indices, hoisting that separated a while loop's count from its loop). All are fixed with regression tests; the JIT call dropped from 4.2 to 3.2 µs and adaptive refinement now runs in place. 1 460 tests passed at the close.

Landed between Tiers 2 and 3

  • Sparse matrices in Function signatures (C-119). sc.S(name, pattern) puts the pattern in the signature: the body receives a SparseMatrix, evaluation takes and returns SciPy matrices with exactly that pattern, and the C signature carries only the values vector.
  • Derivatives with respect to non-input expressions (C-120). Forward mode and sparsity analysis previously returned zeros without error when differentiating in a slice of an input (e.g. a Newton step inside a while_loop body). Such wrt now get a stand-in input.
  • Compiler flags (C-107). JIT default -O2, plus -ftree-vectorize for GCC before 12 only; -O3 was measured and rejected (1–5.8× compile time on large sources).
  • macOS run (C-118) and a fix for a JIT cache race.

Tier 3 · PIQP as a generated interior-point solver

scaly.solvers.ipm implements PIQP 0.6.2 over one sparsity structure, from Ruiz equilibration to the result, as a single generated Function. The solver is written once in Python; the structure (patterns and which bounds exist) is fixed at generation time and the values are inputs.

  • QPStructure fixes the patterns and bounds; QPValues.preprocess applies PIQP's preprocessing (free rows, packed box bounds).
  • ruiz/scale: Ruiz equilibration as a while_loop, with each backend's cost-scaling behaviour reproduced.
  • KKT and Kernels: a dense backend (condensed Cholesky) and a sparse backend (SparseLDL on the full KKT matrix), with PIQP's factorization retries and iterative refinement.
  • Solver(structure, backend, Settings()).solve(values, trace=...): initial point, Mehrotra predictor–corrector, proximal updates, boundary shift, fine-tune switch and infeasibility detection; results in PIQP's layout and status codes, with an optional per-iteration trace.
  • Compiler additions: loop-invariant while_loop(..., params=...) inputs with forward/reverse derivatives and sparsity through them (C-112); outputs may be named like inputs (C-125); SparseLDL.solve_with for a factor carried out of a loop; a leaner call layer with one workspace per thread.

Documented deviations from PIQP

  • The dense backend also fails a Cholesky pivot below ε times its diagonal entry when refinement is off, since its sign is rounding noise.
  • A bound declared finite that arrives infinite or NaN stops with INVALID_BOUNDS (−11), because the solver is specialised to which bounds exist.

All other PIQP quirks (signed box maxima, the cost-scaling aliasing, IEEE 0/0) are reproduced deliberately.

Review round

Five read-only reviewers (fidelity, IR/lowering/JIT, AD through while params, performance, tests and docs) found crashes (colliding derivative Function names, a cold-cache compile race), wrong or stale numbers (dense cost scaling, garbage after a failed first factorization, stale state on infeasibility exits), resource issues (a 1.7 GB table broadcast, a 510 MB file leak in the harness) and a benchmark-fairness issue in compiler flags. All are fixed; ten mutants were all killed. Four exact speed-ups (four-lane max/min reductions, run-by-run sorted segment extrema, per-matrix Ruiz maxima, hoisting data out of the step) cut sparse solves by 11–25% at identical iterations. The IPM tests pass with FMA contraction both off and fast.

CasADi's examples, side by side

examples/casadi/ ports 17 of CasADi's own Python examples (CasADi 3.8.0) as <name>_casadi.py / <name>_scaly.py pairs, covering NLPs, QPs, single and multiple shooting, direct and pseudospectral collocation, MHE, system identification and code generation. compare.py runs each variant in fresh processes with an empty JIT cache and reports agreement, code lines, setup and run time, for interpreted CasADi, CasADi with expand + jit under Scaly's flags, and Scaly.

  • Agreement: all 17 pairs agree; the worst is 6e-7 on race_car (bounds versus constraints, 38 vs 35 IPOPT iterations).
  • Run time: Scaly is 2–21× faster than interpreted CasADi on function-evaluation-heavy OCPs and 1.1–1.6× faster than CasADi JIT; it is 1.2–1.6× slower on millisecond NLPs, where IPOPT time and about 0.35 ms of wrapper glue dominate.
  • Setup: Scaly 0.2–3.6 s (mostly Python lowering) against 2.9–145 s for CasADi JIT, which also ran out of memory on parallel_map and crashed on rocket.
  • Code size: comparable line counts on every pair.
  • Not ported, for Scaly reasons: adaptive integrators (CVODES/IDAS), root-finding on unsymmetric systems (no general dense LU yet), differentiation through solver calls, Python callbacks.
  • Hotspot found: sysid multiple shooting (4 004 variables, arrowhead Hessian) spends 12.6 of 13.5 s of solver construction in star coloring.

Timings are from a 2-vCPU cloud Xeon, not the reference machine used on the results pages.

TinyMPC in Scaly

examples/tinympc/ writes TinyMPC's ADMM for linear MPC with box and second-order-cone constraints once in Python; Scaly generates C specialised to each problem, with dimensions, horizon, dynamics and the Riccati cache folded in as constants. One call is one tiny_solve: a while_loop over ADMM iterations around two scans (backward pass with negative strides, rollout), with warm-start state passed in and out.

  • solver.py (under 300 lines with comments): build_solver(problem) returns one Function (state, x0, xref, uref, bounds…) → (state_next, iterations, solved, u0). Box clipping, cone projections (where, sqrt), norm_inf residuals and the stopping test are plain expressions over the whole horizon.
  • Disabled bounds are not inputs, and cone code is generated only for declared cones. Options: fixed_bounds makes the bounds constants; lowering="block" keeps stage steps as loops over constant tables instead of straight-line code.
  • problem.py holds the Riccati cache as the library computes it and a line-by-line NumPy port of the library's solve, used as the test oracle. tests/integration/test_tinympc.py has 10 tests; 11 of 12 mutants are killed (the survivor, Pinf for Pinfᵀ, is equivalent up to rounding).

Benchmark method

  • Library: TinyMPC at commit 023f36b (2 Sep 2026), built from source, adaptive ρ off. The only patch removes the std::cout printed on convergence, which would otherwise be timed.
  • Problems: the three families of mcu-solver-benchmarks as closed-loop scenarios with their published data and sweeps. Random QP-MPC sweeps nx 4–32, nu 4–32 and N 4–50. The safety filter (double integrator) sweeps nx 2–32 at N = 10 and N 4–100 at nx = 10. Rocket landing with a thrust cone sweeps N 2–256. That makes 52 instances of 100–301 MPC steps each.
  • Same numbers on both sides: the library is set up on each instance and its own Riccati cache is built into the generated solver. The closed loop is run once with the generated solver, and a C++ driver (library) and a C driver (Scaly) then replay the recorded sequence of warm-started solves, so both solve exactly the same QPs.
  • Timing: only the solve call, with clock_gettime; 5 runs of each episode from a zero workspace; the median episode total divided by the number of steps. Bounds are run-time inputs on both sides.
  • Build: both sides with gcc 11.4 at -O3 -mcpu=native -fno-math-errno (and again at -O2), Eigen with -DNDEBUG. Sizes are from size on the objects; compile times are the best of three.
  • Caveat: the machine is an Apple-silicon Mac running a 4-core Linux VM, not a microcontroller, and both sides run in double precision. The float builds TinyMPC uses on microcontrollers are not covered.

Reading the numbers

  • Where the generated code wins. The stage steps are matrix–vector products with constant matrices. Scaly expands small ones into straight-line code with the entries as literals, so structural zeros cost nothing. The double integrator's A, B, K and Quu⁻¹ are block-structured, which is why the safety filter's advantage grows with dimension. With fixed sizes the horizon loops have no bookkeeping, the library's dynamic Eigen matrices are gone, and so are the copies of vnew/znew the library makes every iteration for adaptive ρ even when it is off.
  • Where it loses. The random QP-MPC with 16–32 inputs converges in 4–7 iterations per solve, and each iteration is dominated by dense 16–32-wide products (Quu⁻¹, Kᵀ). Eigen's vectorized kernels beat the scalar sums of the expanded code there (C-117), and packing the carry costs more per solve when there are so few iterations.
  • The loop carry. A while_loop body used to read only its carry, so the references and bounds were copied at every iteration. Making the bounds constants (--fixed-bounds) saved 2–6% of solve time (2.73 → 2.63 ms at nx = 32; 18.4 → 17.9 µs at nu = 32). This measurement motivated the loop-invariant params added in Tier 3 (C-112).
  • Code size and compile time are not monotone in problem size. Below Scaly's expansion limits, a whole stage step (for small problems the whole iteration) becomes straight-line code; above them it stays a loop. That produces the 40–65 KiB peaks at nx = 4, nx = 32 and nu = 32, and the 2–5 s compiles at nu ≥ 24. lowering="block" keeps the loops (35 KiB and 0.3 s at nu = 32) at some cost in speed.
  • Compile time overall: 0.13–4.97 s per instance for Python generation plus gcc -c, against 7.6 s to compile the library once for all problems (its sizes are run-time values).

Fidelity, and library quirks reproduced on purpose

Inputs agree to 3e-13 on the QPs. On the rocket they differ by up to 2e-5 because the library computes part of its cone projection in float; with that made double the difference falls to 9e-14. To compare iterates, the port keeps five places where the library departs from textbook ADMM:

  • the linear cost uses (Q + ρI)·xref, because the stored Q is the penalized diagonal;
  • one ρ is folded into the Riccati cache however many constraint sets act on a variable (box and cone on the rocket's thrust), so the primal step is not the exact augmented-Lagrangian minimizer there;
  • the SOC projection takes float μ and norm, and projects in a metric that scales the cone axis by μ;
  • termination tests only the box slacks, so the applied thrust can leave the cone by up to 0.09 at tolerance 1e-2;
  • the header names the arguments of tiny_set_cone_constraints in the opposite order to the definition, and the library's own rocket example passes them the wrong way round.

Iteration counts are those of today's library, which reorders the ADMM steps relative to the version behind the published result sheets (for the safety filter at nx = 4, N = 10 the sheet reports 18 iterations per solve; today's library and the generated code both take 232 on average).

The port also found C-125: an output named like an input was read back from the output buffer, giving silently wrong numbers. It was fixed in Tier 3.

What comes next

Tier 4 decisions

  • Parity semantics for the drop-in backend="scaly" (decision traces plus tolerances), and which PIQP quirks it keeps.
  • Baselines and the SQP corpus (chain, race_cars, npmpc, unbumpercars).
  • Implicit QP sensitivities reusing the final factorization.

Performance levers

  • C-114 unpadded sparse factor updates (1.6–1.7× in a prototype).
  • C-117 a blocked dense Cholesky with register-tiled kernels.
  • C-131, C-134 loop-carry copies and step overheads (a further 5–10%).
  • C-130 QRECIPE's sparse path takes 34 iterations against PIQP's 19.

Example ideas not yet written: nonsmooth_conventions, sensor_localization, goddard_rocket, minimal_surface. Known issue from the gallery: building sc.solver(sc.qp_problem(n, 1, n), "piqp") grows steeply with n (14.4 s at n = 200), mostly in solver construction.
