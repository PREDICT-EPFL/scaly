Case study E6 · AC optimal power flow (PGLib-OPF, JuMP, ExaModels)

Plan case_studies_plan_2026_09_27.html, E6 · branch claude/case-studies · 28 Sep 2026 · code in examples/case_studies/acopf/

Summary. rosetta-opf's AC-OPF model through JuMP, through ExaModels, and generated by Scaly, on seven PGLib-OPF cases from 14 to 13 659 buses. All three run the same Ipopt build (3.14.19) with MUMPS, from the same processed data.

  • The same solves. Every case takes identical Ipopt iterations (JuMP one fewer on case13659) to the same objective. Scaly's equals JuMP's to every printed digit.
  • Derivatives. Scaly's function evaluations are 10.6× below JuMP's at case1354 and case2869, and within 1.3× of ExaModels' up to case1354.
    • From there Scaly falls behind ExaModels: 1.7× at case2869, 4.4× at case9241 and case13659.
    • The cause is the Hessian's colour width. It follows the largest bus degree (12 → 74), so the work grows as variables × colours. ExaModels' per-pattern local Hessians grow as nonzeros.
  • The whole solve. Scaly and ExaModels are level (Scaly at 0.88 to 1.06× ExaModels' time), and both are 1.4 to 2× faster than JuMP. MUMPS is most of what remains.
  • Time to a first solution. Scaly is the fastest up to case2869 (1.5 to 8.9 s) and the slowest at case9241 and case13659 (53 and 66 s, against 24 and 29 s for ExaModels). The same colour width produces 277 MB of C there.
  • Colouring itself did not block the study, although the plan had made it a prerequisite. sc.solver builds the 117k-variable case13659 in 3.7 s. What does not scale is how many colours the model needs.

Against the plan's success criteria: "derivative time within 1.5× of ExaModels on CPU and at least 10× below JuMP" is met up to case1354 and not met from case9241 (4.4× ExaModels, 4.1× below JuMP). "Setup below 5 s up to 10k buses" is met up to case1354. "Identical Ipopt iterations against JuMP" is met on six of seven cases, and within one iteration on the seventh. "Match the PGLib reference objectives to 1e-6" is met to the five digits PGLib publishes. The objectives are compared with JuMP's to 1e-12 instead.

1. The benchmark and the reproduction

  • Upstream.
    • rosetta-opf at 496d026: jump.jl and examodels.jl, the models the ExaModels paper's AC-OPF comparison uses.
    • PGLib-OPF at v23.07.
    • Julia 1.10.12 with PowerModels 0.21.6, JuMP 1.31.2, Ipopt.jl 1.16.0, ExaModels 0.12.0 and NLPModelsIpopt 0.11.3.
    • Ipopt_jll 300.1400.1902, which is Ipopt 3.14.19, the version Scaly's plugin builds. This removes E1's IPOPT-build confound.
  • One change to upstream code. examodels.jl was written for ExaModels 0.7. That version needs an older NLPModels stack, whose Ipopt.jl in turn requires Ipopt 3.14.16. examodels_v0.12.patch renames its calls to 0.12's (@add_var, @add_con, @add_con!), with the same model and data code, so all three stacks share one Ipopt. jump.jl runs unmodified.
  • Options without editing the models. Ipopt reads ipopt.opt from the working directory, so the tolerance (1e-8 and the paper's 1e-4), mumps and the timing statistics come from there. Scaly gets the same values.
  • Same data. export_case.jl writes each case as PowerModels processes it for rosetta-opf, in the order JuMP iterates it: per unit, corrected angle limits, quadratic costs, thermal limits. The Scaly model reads that, so the three models have the same variables in the same order.
  • Same timers. Every process solves the case twice and records the second solve; the Julia processes first solve rosetta-opf's warm-up case. All three are timed by Ipopt's own timing statistics, parsed identically.
    • This also fixes a problem the plan noted in the paper: ExaModels' numbers there are wall time, while AMPL's and JuMP's are Ipopt CPU time.

Scaly evaluates the Lagrangian Hessian and the constraint Jacobian by colouring: one sweep of the whole model per colour. On these networks the colour width follows the largest bus degree, which grows with the network, so evaluation and generated code grow as variables × colours. ExaModels forms each constraint pattern's local Hessian (a 4 × 4 block per branch equation) and scatters it, which grows as the number of nonzeros. From case2869 to case9241 (3.4× the variables), Scaly's Hessian per iteration grows 10×, ExaModels' 3.5×.

4. What the numbers say about Scaly

  • L1 (vectorized derivatives) delivers against the modelling layer. Against JuMP, Scaly removes 82 to 91% of the derivative time up to case2869. The whole solve then comes out 1.4 to 2× faster than JuMP's, as fast as ExaModels'. That is the plan's "40 to 60% less total time at the same Ipopt and linear solver", met through case2869.
  • Colouring is the wrong tool for many copies of one small pattern. ExaModels' SIMD abstraction is exactly this benchmark's point. The plan read "the colouring must scale" as a speed problem in star_coloring, but that part is fine. What grows is the number of colours, and every colour costs a full sweep and its own code. CS-5 in todo.md is rewritten with these measurements: form the local derivatives of a vmap body, or of one gather pattern, and scatter them.
  • Setup is fast for small models and slow for large ones, for the same reason. The 277 MB of C at case9241 is the colour width written out.
    • Up to case2869, no JIT and one compiled C file beat Julia's package and model compile: 1.5 to 8.9 s against 4.7 to 13 s.
    • From case9241, generating and compiling 277 MB loses to ExaModels' generic compiled kernels.
  • The linear solver now decides. With derivatives cheap, 77 to 88% of Ipopt's time is MUMPS on both ExaModels and Scaly. Beating ExaModels on CPU at scale needs a faster KKT solve, as the plan expected.

5. Tests and checks

  • New test. tests/integration/test_case_study_acopf.py builds the same model for a 3-bus network with a phase-shifting transformer (tap 1.05, 3°), a line-charging split and a bus shunt. Scaly's IPOPT solution is checked two ways, neither sharing the formulation:
    • against the power-flow mismatch from a bus admittance matrix (below 1e-8);
    • against SciPy's SLSQP on the problem written with that matrix (objective to 1e-7, point to 1e-5).
  • Mutation checks: 5 of 5 killed.
    • The phase-shift sign.
    • The tap ratio dropped on the from side.
    • The to-side sine sign.
    • The shunt's reactive sign.
    • Arcs attached to the wrong buses.
  • Study gates. Identical iterations and objectives across the three stacks, in results/sweep.json. In the notebook, case118's solution is checked against an independent admittance matrix (2.1e-10 p.u.).
  • Suite. The node-ID baseline is regenerated (+1). Nothing under src/ changed.

6. Fairness notes and what was not done

  • Machine. Not the reference machine. One-thread MUMPS on every side; Julia on one thread.
  • ExaModels runs through Ipopt here, not MadNLP, its paper's pairing. The comparison is therefore of the modelling layers at the same solver. MadNLP's own linear algebra would change the whole-solve column, not the derivative column.
  • MUMPS, not MA27. There is no HSL licence here, so every side uses the same solver. The paper used MA27.
  • The patch for ExaModels 0.12 renames calls only. It is the same model as ExaModels' own documentation example for 0.12, and it takes JuMP's iterations on every case.
  • Not done.
    • MadNLP and the GPU column.
    • case30000, where the colour width would grow further.
    • The 24-period extension with ramping coupling.
    • A Python MATPOWER reader, which the plan listed: PowerModels' export is the source of truth here, and two exported cases ship for the notebook.
