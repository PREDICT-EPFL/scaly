O4: one instruction for a NaN-propagating max or min

Step 4 of the generated-code speed plan · todo C-199 · branch perf/codegen-speed · 30 Sep 2026 · Apple M3 Max, Apple clang 21, the JIT's flags

Summary. A max or min reduction propagates NaN as np.max does, which C's fmax does not, so each step was the select ((cur < x) || (x != x)) ? x : cur: two dependent compares and a select, 851 of them in the generated QAFIRO solver (norms, step lengths, residual maxima). AArch64 has the NaN-propagating maximum as one instruction, and clang exposes it; the renderer now spells the select that way where the compiler can.

  • Speed: the generated IPM QAFIRO sparse 1.16× faster, HS118 dense 1.09×, CVXQP1_S dense 1.07×, the sparse MPC 1.06×; elementwise_1e5 1.02×. That is -ffinite-math-only's whole gain on these kernels, without its license to assume no NaN.
  • Semantics: the builtins are IEEE 754-2019 maximum/minimum: a NaN operand gives NaN, and −0 counts below +0 where the select kept the first of two zeros. Only a zero result's sign can differ, which the reductions' four lanes already leave open. Float32 reductions keep the select (the builtins would give the expression a double's type).
  • Portability: the macro is defined only in a source that uses it, after the vector typedef, behind __has_builtin; GCC, older clang and any other compiler get the select as a static inline function. Checked: Apple clang 21 (C, C++), GCC 15 at -std=c99 -Wall -Wextra -Werror.
  • Tests: 4 428 passed, 57 skipped, 5 xfailed (2 new). Seven mutants, seven killed. Snapshot control.c regenerated.
  • Undo: git revert the commit “Codegen speed O4”.

What changed

  • codegen/c.py: _nan_extremum recognizes the float64 select of a max step, select((cur < x) || (x != x), x, cur), and of a min step, select((x < cur) || (x != x), x, cur), by node identity (both dialects are hash-consed), and _emit_scalar renders it as SCALY_FMAX_NAN(cur, x) or SCALY_FMIN_NAN(cur, x). with_prelude inserts the definitions (_NAN_EXTREMA) into a finished source that uses them; render_program_c and the solver-bearing path in codegen/aot.py both pass their source through it.
  • The lowering is unchanged: the renderer still makes no lowering decision, it spells one it recognizes.
  • docs/how_it_works/lowering.md: the spelling and the zero-sign caveat.
fcmp  d1, d1            ; today: x != x
fccmp d0, d1, #8, vc    ;        cur < x, if ordered
fcsel d0, d1, d0, mi

fmax  d0, d0, d1        ; __builtin_elementwise_maximum(cur, x)

Tests and mutation checks

  • tests/core/codegen/test_c.py: the macros appear, with their definitions after the typedef, exactly in a source with an extremum reduction, and no NaN test is left in its body; a source without one has neither; a float32 reduction keeps its select. Both spellings compiled from one source (the builtin test switched off for the second) give NumPy's maximum, minimum and infinity norm, NaN at the first, a middle and the last element included, and agree with each other.
  • The existing four-lane extremum tests (NaN in every position, lengths 1 to 1 001) run through the builtins on this machine.
