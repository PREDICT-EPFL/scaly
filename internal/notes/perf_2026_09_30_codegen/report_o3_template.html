O3: FMA contraction across statements, measured and rejected

Step 3 of the generated-code speed plan · todo C-198 · branch perf/codegen-speed · 30 Sep 2026 · Apple M3 Max, Apple clang 21

Summary. No change to the code. The plan's third step was to let clang contract a multiply and an add that sit in different statements, which GCC does by default and clang does not (-ffp-contract=fast against clang's on, which contracts inside one expression only). On the base code it measured 0.97 in geometric mean and up to 0.80. After O2 it measures 1.11, slower: the partial sums O2 introduced run up to 2.3× slower under it.

  • Decision: the JIT keeps clang's default. Nothing to revert; the step is recorded so it is not tried again for the same reason.
  • Not touched either way: the benchmark protocol's flags (HOST_CFLAGS, which the sweep compiles both providers with). docs/results/fairness.md explains why contraction there is a choice with consequences for the comparison with CasADi SX, whose one-operation statements clang cannot contract today; that choice is not a speed step for the generated code.

The measurement

Every corpus kernel after O2, compiled with the JIT's flags, then with -ffp-contract=fast added, then with -ffinite-math-only (O4's evidence) and with -ffast-math for reference. Seven interleaved rounds, fastest sample.

What slows down is exactly what O2 sped up: matvec_256 (2.31), mlp_big_fwd (2.06), npmpc (1.50), unbumpercars (1.49), and the scan's gradient (1.20). The partial sums are statements of the form s1[0] = (s1[0] + (a[k+1] * x[k+1])), contracted already under clang's default because each is one expression; with contraction across statements the compiler no longer pairs the four lanes into vector operations. Under -ffast-math, which also reassociates, the same kernels are 1.1–1.2× slower than the JIT build, so the generated order now beats the compiler's own reordering there.
