O1: scalarize an entry point that calls nothing

Step 1 of the generated-code speed plan · todo C-197 · branch perf/codegen-speed · 30 Sep 2026 · Apple M3 Max, Apple clang 21, the JIT's flags

Summary. The entry point of a generated function was never scalarized automatically, only its callees were. A standalone kernel, such as the Jacobian of a small model written without calls, therefore ran as loops over buffers, multiplying by identity-seed tables of zeros and ones that C is not allowed to fold (0.0 * x is not zero for an infinite or NaN x). Scaly's own folding does, so an entry that calls nothing now expands like a callee does.

  • Speed: quat_jac 1.97× faster (12.2 → 6.2 ns), cartpole_jac 1.28× (74.9 → 58.6 ns), rosen_hess 1.20× (1.6 → 1.3 ns). The other 23 corpus kernels generate byte-identical C.
  • Code: quat_jac 115 → 73 lines, cartpole_jac 337 → 172, rosen_hess 58 → 32. Generation time unchanged (a 4 096-unit work cap keeps a doomed attempt from costing up to 2.7 s; mlp_small_jac's rejected attempt had cost 0.43 s before the cap).
  • Tests: 4 398 passed, 57 skipped, 5 xfailed (3 new tests). Five mutants, five killed. Two C snapshots (forward.c, jac.c) regenerated as the deliberate change; nine loop-form pass tests now ask for loop form with .block().
  • Undo: git revert the commit “Codegen speed O1”.

What changed

  • passes/lowering.py: the entry is lowered with the same scalarize mode as any procedure (the auto_scalarize=False special case is gone) and marked entry on its PROC.
  • passes/program/scalarize.py: under auto, an entry that calls a procedure, in a loop (a vmap, a scan) or once, keeps its loopy form, as before; one that calls nothing expands under the callee budgets (4 096 operations, 16 384 of growth program-wide) and a work cap of its own, AUTO_EXPANSION_WORK_PER_ENTRY = 4096. A rejected attempt costs about 40 µs of generation per unit of work, and the accepted entries in the corpus need at most 2 772 units; the callee cap stays 65 536.
  • docs/how_it_works/lowering.md: the policy.

What the change does to a kernel, from the forward snapshot (a four-state step with a reduction and a concat):

- double s0[1]; double s1[1];
- s0[0] = 0.0;
- for (long long i_t7 = 0; i_t7 < 2; ++i_t7) { double v0 = t2[i_t7]; s0[0] = (s0[0] + (v0 * v0)); }
- s1[0] = (0.10000000000000001 * s0[0]);
- for (...) { res[0][j] = (t0[j] + (0.050000000000000003 * t2[j])); }
- for (...) { ... }
+ double v0 = arg[0][2];
+ double v1 = arg[0][3];
+ double v2 = (0.10000000000000001 * ((v0 * v0) + (v1 * v1)));
+ *(double2*)(res[0]) = (double2){(arg[0][0] + (0.050000000000000003 * v0)), (arg[0][1] + (0.050000000000000003 * v1))};
+ *(double2*)(res[0] + 2) = (double2){(v0 + (0.050000000000000003 * (arg[1][0] - (v2 * v0)))), ...};

In the Jacobian snapshot the 85 changed lines are the seed tables k0, k1, the four copy loops per seed and the k-loops multiplying by them, all folded away.

Tests and mutation checks

  • New in tests/core/passes/test_scalarize.py: an entry that calls nothing expands and no seed survives as a multiplier (against the analytic Jacobian); an entry that calls a procedure once keeps the call while the callee expands; the entry's work cap against a callee's, on the file's own policy procedure whose work is exactly 3 * count.
  • Loop-form tests that probe a pass through a tiny entry (fusion, aliases, scatter sums, affine tables, the four-lane extremum, the viz listing, the SpMV loop bound) now request loop form with .block(), the documented hint, instead of relying on the entry never expanding.
  • Snapshots forward.c and jac.c regenerated with python -m tests.core.test_c_snapshot; wide.c and the rest unchanged.
  • Full suite: 4 398 passed, 57 skipped, 5 xfailed. ruff format, ruff check clean; ty check reports the same 144 diagnostics as the base worktree, none in touched files.
