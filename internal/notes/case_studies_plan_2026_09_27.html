Scaly case studies: eight published benchmarks to reproduce

Plan · 27 Sep 2026 · survey of 2016–2026 papers whose results hinge on fast computation, with a reproduction plan for each

Goal. Reproduce 5–10 published case studies twice: once with the tool the authors used, and once with Scaly. Each should show one of Scaly's advantages on a problem someone else chose. That rules out benchmarks built to flatter Scaly.

Selection rule. Each study had to meet three conditions:

  1. The code is public, so the baseline can be rerun on the reference machine.
  2. The paper reports timings that separate the computation Scaly changes.
  3. The bottleneck is something Scaly can plausibly change. One of the eight, E8, needs a feature Scaly does not have yet, and is flagged as such.

Five are in control and robotics (E1–E5). Three are outside control: power systems (E6), vision and robotic state estimation (E7), and aerospace guidance (E8).

Where Scaly can win

Every expected gain below is one of these six levers. Each example names the levers it relies on.

Common protocol

  • Layout. Each study lives in examples/case_studies/<name>/, with the pieces below. This follows the pattern of examples/casadi/compare.py and examples/tinympc/benchmark.
    • baseline/: the upstream repository pinned by commit, plus a setup script.
    • scaly_impl.py.
    • compare.py: runs each variant in a fresh process with an empty JIT cache.
    • README.md with the results table.
    • A notebook with plots and a generated-C cell.
  • Two levels of comparison where possible.
    • Drop-in: the paper's own solver (acados, IPOPT, Fatrop) with only the oracles replaced by Scaly's. This isolates L1 and L2, and the iteration counts must match exactly.
    • Full stack: Scaly's own generated algorithm. This shows L3 and L4.
  • Fairness. docs/results/fairness.md governs every run: reference machine, five fresh processes, the same compiler and flags, the same solver build and linear solver on both sides, and every failed attempt kept.
    • Published numbers appear only as context, in a separate "paper reports" table. They are never mixed with our measurements.
    • Every pair gets an agreement check: solution difference, iterations, and objective against the paper's value.
  • What is always reported.
    • Setup time: generation, compilation, and JIT for JAX or Julia.
    • Runtime: function evaluation separately from the linear solve.
    • Generated source size and .text size.
    • Peak compiler memory.
  • Tests. A small instance of each study goes into tests/integration/, compared against a NumPy reference, so that no benchmark is the only thing exercising an IR, AD or codegen path.

E1 · Hanging chain and manipulator NMPC (Fatrop / acados)

robotics / NMPCL1 L2effort M

Paper and key computation

Fatrop1 benchmarks Fatrop, acados and IPOPT on OCPs written in rockit/CasADi SX with RK4. The problems are:

  • minimum-time problems: manipulator, truck with two trailers, quadrotor with obstacles;
  • MPC problems: hanging chain in 2D and 3D, quadrotor, cart pendulum.

The paper's horizons are K = 25–100 and its state dimensions are up to 39. The computation that matters is the RK4 sensitivities and the exact Hessian of the Lagrangian at every stage.

What the paper reports (i7-10850H)

ProblemFatrop, msacados, msIPOPT, ms
Hanging chain 2D (MPC)7.615.2260.48
Hanging chain 3D (MPC)17.629.7683.96
Robot manipulator (min-time)35.51–136.65
Truck with two trailers (min-time)30.32–135.63

For the hanging chains, "compilation failed due to insufficient available memory". The CasADi virtual machine was used instead, and function-evaluation time was excluded from the totals1. The acados paper's chain benchmark (M=5, N=40, SQP-RTI) reports a median of 1.05 ms per iteration, but it does not split derivatives from the QP2.

Why Scaly should do better

  • This is the problem family where the repo's own benchmark shows the crossover. SX hits the compile limit at chain M=9, where Scaly is 4.46× faster than mapped SX. Scaly's closed-loop SQP spends 55% less total time than CasADi on the chain.
  • A chain that CasADi cannot compile, and runs only in the virtual machine, is the clearest possible L2 demonstration.
  • For small chains (M ≤ 5), SX is currently 2.5× faster than Scaly. The sweep has to show the crossover honestly.
  • Gauss–Newton acados needs only first-order sensitivities, so the L1 gain shrinks there.

Implementation plan

  1. Pin fatrop_benchmarks and rockit, then reproduce Tables III–IV on the reference machine. Record whether the chain compiles, and its compile time and peak RSS.
  2. Port the chain (2D and 3D), manipulator, truck–trailer and quadrotor-obstacle OCPs to Scaly.
    • Use sc.integrators RK4, with stage functions as templates and vmap over stages and masses.
    • Check that the dynamics match rockit's numerically to 1e-12 at random points.
  3. Drop-in, IPOPT. Run the Scaly IPOPT plugin against rockit's IPOPT with the same build, linear solver and tolerances. Require identical iteration counts, then compare function-evaluation time.
  4. Drop-in, acados. Export the dynamics, their sensitivities and the exact Hessian with scaly_codegen --casadi as acados generic external functions, keeping HPIPM and partial condensing the same. Compare acados' time_lin and time_sim. Check early that acados' generic path accepts Scaly's CasADi-layer symbols.
  5. Drop-in, Fatrop. Feed Scaly stage functions through Fatrop's C++ OCP interface, or as casadi.external nodes inside rockit. Whichever is less invasive, prototype it on the cart pendulum first.
  6. Full stack. Run scaly-sqp with PIQP now, and with the generated IPM once Tier 4 lands.
  7. Sweep chain size M = 3…15 and plot, for CasADi SX, mapped SX, MX and Scaly: function-evaluation time, compile time, source size and peak compiler memory.

Success: identical iterates in the drop-in runs, and function-evaluation time and compile time better than the best CasADi encoding from M ≈ 7 up. The 3D chain should compile to C where CasADi's C does not.

E2 · Neural-residual quadrotor MPC (Real-time Neural MPC / L4CasADi)

learning-based controlL1 L3 L6effort M

Paper and key computation

The paper3 models a quadrotor with 13 states (position, quaternion, velocity, angular velocity) and 4 rotor thrusts, plus a learned MLP residual. It is controlled by acados SQP-RTI with N=10 and RK4. There are two ways to include the network:

  • Naive: the MLP is expanded symbolically in CasADi.
  • RTN-MPC: PyTorch evaluates the network and its Jacobian at the shooting nodes, and passes a first-order Taylor surrogate to acados as parameters.

The key computation is the network's value and Jacobian inside the RK4 stages.

What the paper reports (Table II, i7 CPU, control frequency in Hz)

MLPNaive CasADiRTN-MPC (Taylor surrogate)
no network42624262
2 layers × 1622281096
5 × 161139885
2 × 1281161071
5 × 12831784
12 × 32168588
12 × 51211507

Why Scaly should do better

  • The naive path collapses because CasADi expands every weight into the scalar graph. Scaly keeps the layers as dense loops, differentiates them exactly through those loops, and loads the same PyTorch weights (scaly.utils.load_torch_state_dict). The repo's neural-process MPC benchmark is already 8.5× faster than MX on this pattern.
  • RTN-MPC gives up model exactness and needs libtorch at runtime. It also loses to naive CasADi on small networks: 1096 against 2228 Hz, which is the call overhead. Scaly should beat both columns for widths up to about 128, and do so with the exact model.
  • Deployment footprint (L6): self-contained C in place of libtorch, which is hundreds of MB.
  • 12 × 512 is bounded by floating-point work. Exact Jacobians at every RK stage cost tens of ms whatever the tool. There, the fair comparison is Scaly running the same Taylor surrogate in C, and the expected result is parity to a modest gain, not a large one.

Implementation plan

  1. Clone TUM-AAS/neural-mpc and ml-casadi, and reproduce Table II on the reference machine with torch pinned to one CPU thread. Include the trained checkpoints, or retrain from their data if they are not shipped.
  2. Write the Scaly model: quaternion rigid-body dynamics plus an MLP residual, loaded from the same state dict. Check that the residual matches PyTorch to 1e-12.
  3. Variant A, drop-in: export the exact dynamics and Jacobians to acados as generic external functions, with the same RTI and HPIPM.
  4. Variant B, surrogate in C: the network's value and Jacobian at the N nodes as one vmapped Function. This is the same algorithm as RTN-MPC with torch removed.
  5. Variant C, full stack: scaly-sqp in RTI mode with PIQP, through sc.mpc once it lands.
  6. Replay the paper's closed-loop tracking scenarios. Report frequency per network size, the share of time in function evaluation, tracking RMSE (exact against surrogate), and binary size.

Success: Variant A at or above the RTN-MPC column for every width ≤ 128 while using the exact model, and Variant B at least equal to RTN-MPC at 12 × 512.

E3 · Embedded convex MPC QPs (CVXPYgen / QOCOGEN / Conic-TinyMPC)

embedded optimisationL4 L2 L6effort M

Papers and key computation

CVXPYgen5 generates C for parametrised convex problems. Its benchmarks are a quadcopter MPC (6 states, 3 inputs, H ∈ {6, 12, 18, 30, 60}) and a portfolio back-test. The paper reports:

  • CVXGEN cannot generate code beyond H = 18.
  • Canonicalisation costs about two orders of magnitude less than the solve.
  • Absolute times appear only in figures.

QOCOGEN6 is the closest prior work to Scaly's generated PIQP. It fixes the sparsity pattern, runs AMD at generation time, and emits an LDLᵀ with only the necessary operations, using static memory. Its appendix compares that LDLᵀ with QDLDL on an LQR KKT matrix (6 states, 3 inputs):

Horizon T5155075100
QOCOGEN unrolled LDL, µs0.441.786.128.4912.9
QDLDL, µs2.107.5127.138.849.6

The authors state that generated code size grows with the problem, so the custom solver was tested only on small instances.

Conic-TinyMPC8 reports that OSQP runs out of memory on an STM32F405 at N ≥ 32.

Why Scaly should do better

  • The same specialisation as QOCOGEN, but stages from vmap stay loops, so the code does not grow with H. That attacks QOCOGEN's and CVXGEN's stated limit directly.
  • The parameter-to-KKT update is fused into the same function. The gain is small, given the roughly 1% canonicalisation share.
  • PIQP's proximal IPM stays reliable at high accuracy, where OSQP needs many iterations.
  • At small H, expect parity with QOCOGEN and CVXGEN. A warm-started OSQP at low accuracy in closed loop may win.
  • The SOCP instances are excluded until E8's conic extension exists.

Implementation plan

  1. Reproduce CVXPYgen's quadcopter MPC and QOCO's oscillating-masses and MPC families from qoco-benchmarks. Generate the OSQP, QOCOGEN and Clarabel variants through CVXPYgen, and time them from C with a harness like examples/qp_solvers/time_entry.c.
  2. Write the same families as parametric sc.problems. Solve them with the generated PIQP (examples/qp_solvers/generated_piqp.py, and backend="scaly" once Tier 4 lands) as well as the PIQP library.
  3. LDL microbenchmark: Scaly's generated sparse LDLᵀ on the identical LQR KKT, T = 5…100, against QDLDL and QOCOGEN's emitted code. This reproduces the table above.
  4. Sweep H up to 200 at matched tolerances (1e-3 and 1e-6). Report solve µs, iterations, source and .text size, and generation-plus-compile time. Record where each competitor stops generating.
  5. Embedded leg: cross-compile the Conic-TinyMPC predictive safety-filter QP for a Cortex-M7 (Teensy 4.1) and an STM32F4. Report flash, RAM and µs against OSQP and TinyMPC.
  6. Fix the known build-time growth of sc.solver(sc.qp_problem(n, …), "piqp") (0.23 s at n=50, 14.4 s at n=200) before the sweep. Otherwise setup time will dominate the story.

Success: the LDL within 1.5× of QOCOGEN's unrolled code at small T and faster than QDLDL throughout. The whole solve faster than every CVXPYgen backend for H ≥ 30. The largest H compiles where CVXGEN and QOCOGEN are not attempted.

E4 · Constrained trajectory optimisation suite (ALTRO)

robotics / trajectory optimisationL3 L1effort M/L

Paper and key computation

ALTRO9 is an augmented-Lagrangian iLQR followed by an active-set projection, written in Julia. It was compared with DIRCOL solved by Ipopt and SNOPT. The key computation is dynamics rollouts and derivative expansions inside nested loops: the outer AL loop, iLQR iterations, a backward Riccati pass and a forward line search.

What the paper reports (Table I, i7-6500U)

ProblemALTRO, sDIRCOL (Ipopt), s
Parallel park, N=510.1170.100
Escape2.839.08
Quadrotor maze, N=10123.0559+
Kuka arm with obstacles14.3313*

The authors call this a "preliminary implementation". The current Altro.jl is much faster, so it is the baseline that counts.

Why Scaly should do better

  • The whole AL-iLQR, projection included, becomes one allocation-free C function (L3). examples/ilqr.py already does this for unconstrained iLQR.
  • The same OCP is given to Scaly with IPOPT on a collocation transcription, which reproduces the DIRCOL column with exact sparse Hessians.
  • Current Altro.jl, with ForwardDiff and StaticArrays, is fast for small state dimensions. The expected gain over it is a few ×, not orders of magnitude.
  • The Kuka problem needs rigid-body dynamics, written in Scaly as RNEA as a scan over links. It is optional.

Implementation plan

  1. Extend ilqr.py into an AL-iLQR:
    • penalty and multiplier updates in an outer while_loop;
    • constraint Jacobians per stage through vmap;
    • the active-set projection step with linalg.ldl.
  2. Port parallel park, escape, quadrotor maze and cart-pole from TrajectoryOptimization.jl and ALTRO's problem set, with the same discretisation and tolerances.
  3. Establish the baselines: current Altro.jl, and, if a maintained C++ ALTRO exists at the pinned date, that too. Also run Ipopt DIRCOL from Julia against Scaly with IPOPT on the same collocation.
  4. Report time to solution, iterations, final constraint violation and cost. Add the Kuka arm last, with RNEA, if time allows.

Success: the same local optimum (cost within 1e-6 relative) in less wall time than current Altro.jl on every problem. Scaly with IPOPT should beat Julia DIRCOL on the maze.

E5 · Differentiable MPC in a learning loop (DiffMPC / mpc.pytorch)

learning / differentiable optimisationL5 L3effort M

Papers and key computation

Differentiable MPC11 differentiates through the MPC's fixed point by reusing the LQR factorisations. DiffMPC12 benchmarks four implementations on the same problems:

  • the implementations: mpc.pytorch, trajax, Theseus and DiffMPC, each on CPU and on GPU;
  • the problems: batched MPC within an RL loop, with nx 8–16, nu 4–8, T 30–40 and batch sizes 16–256, each timed over a 50-step episode.

The key computation is batched constrained LQR or MPC solves and the adjoint of their solution with respect to cost and dynamics parameters.

What the paper reports (Table 3, CPU, Threadripper 3990X; thread count not stated)

Problem 1, per episodeForward, sBackward, s
mpc.pytorch1.443.37
trajax0.931.90
DiffMPC (CPU)1.332.70

Why Scaly should do better

  • At these sizes the time goes into Python and JIT dispatch and small dense kernels, not arithmetic. A batch vmapped into one C function removes that overhead (L3).
  • The backward pass is one adjoint Riccati sweep on the active set, attached as an implicit rule to the solver's output (L5). It does not differentiate the iterations.
  • GPU DiffMPC (0.22 s) at large batches is out of scope, so only the CPU comparison is claimed.
  • Scaly is single-threaded. Parallelise across batch chunks only if the baselines use multiple threads.

Implementation plan

  1. Reproduce the DiffMPC benchmark scripts on CPU, with the thread count fixed and stated for every baseline.
  2. Implement the same solver class DiffMPC uses (read from its repository) as a while_loop. Attach the adjoint as an implicit rule on the solution through the existing custom-rule mechanism (docs/guide/derivatives.md, implicit rule).
    • This needs a small public API for "implicit rule on a composite Function". Today it exists only as _from_exprs.
  3. vmap over the batch. Validate gradients against finite differences and against DiffMPC to 1e-8.
  4. Avoid the known slow path: reverse through SparseLDL.solve with a matrix right-hand side is about 100× slower. Use per-column solves or fix that path first.
  5. Report forward and backward seconds per episode for each batch size, single- and multi-threaded, plus the end-to-end learning curve to show that the gradients are the same.

Success: both forward and backward at least 5× faster than the best CPU baseline at every batch size, with identical learning curves.

E6 · AC optimal power flow on PGLib-OPF (ExaModels / JuMP / PowerModels)

power systems (outside control)L1 L2effort M

Papers and key computation

ExaModels13 introduced a "SIMD abstraction": repeated constraint patterns are evaluated as one kernel. That is the same idea as Scaly's vmap. Its benchmark covers 25 PGLib cases15, and compares four stacks: ExaModels with MadNLP, Ipopt with AMPL, Ipopt with JuMP (the PowerModels14 stack), and a GPU run. The key computation is the sparse Jacobian and Lagrangian Hessian of the polar power-flow equations, which are gathers over branch→bus incidence.

What the paper reports (Xeon Gold 6140, MA27, tolerance 1e-4; derivative time / total, s)

CaseExaModels CPUAMPLJuMP
1354_pegase0.06 / 0.700.94 / 1.482.40 / 3.04
10000_goc0.76 / 13.3014.56 / 24.8524.71 / 36.00
13659_pegase0.92 / 16.9419.90 / 35.7935.97 / 53.02

Derivatives are 45–70% of the total with JuMP or AMPL, and about 5% with ExaModels. The ExaModels timings are wall time and the AMPL and JuMP ones are Ipopt CPU time, which a reproduction should harmonise.

Why Scaly should do better

  • Against JuMP, AMPL and PowerModels, Scaly should remove most of the derivative time, which means 40–60% less total time at the same Ipopt and linear solver.
  • Setup latency is a clear win: no Julia JIT. The same holds for batched, multi-period or N-1 problems generated as one vmapped model (as opf_day_ahead does), and for small cases, where one C function beats the modelling-layer overhead.
  • Against ExaModels on CPU, parity is the realistic ceiling: its time is 75–85% linear solver. Beating it needs a faster KKT solve, which is outside this study.

Implementation plan

  1. Prerequisite: the star colouring of the Hessian must scale. On sysid (4004 variables) it takes 12.6 of 13.5 s of sc.solver. Colour one vmap body and replicate it, or make star_coloring near-linear, before attempting 10k-bus cases.
  2. Extend the MATPOWER reader in optimal_power_flow.py to the PGLib-OPF v23.07 files.
    • Write the rosetta-opf/ExaModels polar formulation exactly: angle-difference limits, thermal limits on both ends, and shunts.
    • vmap over branches, buses and generators with index gathers.
  3. Match the PGLib reference objective values to 1e-6 relative on every case.
  4. Run the baselines: ExaModels with Ipopt and MadNLP on CPU, and JuMP with Ipopt (rosetta-opf), all on the same Ipopt build. Use MUMPS on both sides, and MA27 on both if HSL is available. Use tolerances 1e-4 (the paper's) and 1e-8.
  5. Sweep case14 up to case13659, and case30000 if colouring allows. Take the derivative and linear-solver split from Ipopt's timing statistics on both sides.
  6. Extension: a 24-period OPF with ramping coupling as one problem, against the equivalent ExaModels and JuMP models.

Success: derivative time within 1.5× of ExaModels on CPU and at least 10× below JuMP; setup below 5 s up to 10k buses; identical Ipopt iterations against JuMP.

E7 · Factor-graph nonlinear least squares (SymForce, with BAL as a stretch)

robotics / vision (outside control)L3 L4effort M

Paper and key computation

SymForce16 is the most direct code-generation competitor. It flattens factor linearisations into straight-line C++, and in "fixed" mode also fixes the sparsity. Its robot 3D localisation benchmark has 5 poses and 20 landmarks. The key computation per LM iteration is: linearise the factors on SE(3), form JᵀJ, factor it with sparse Cholesky, and take the damped step.

What the paper reports (Table IV, i7-9700K, µs)

ToolLineariseFull iteration
Ceres42.6108.6
GTSAM30.0155.4
SymForce, dynamic15.147.0
SymForce, fixed5.425.6

Why Scaly should do better

  • SymForce fixes the linearisation, but the step still goes through a general sparse solver. Scaly puts linearisation, JᵀJ, the generated LDLᵀ for the fixed pattern and the LM damping logic into one function (L3, L4). pose_graph_slam already matches MINPACK LM to 1e-9.
  • As the graph grows, flattened code grows with it. Scaly's vmap over factors of one type keeps the code proportional to the number of factor types, not factors.
  • At 5 poses everything is cache-resident and SymForce fixed is already strong. Expect 1–2× here. The scaling sweep is where the story is.

Implementation plan

  1. Reproduce SymForce's localisation benchmark with GTSAM and Ceres on the reference machine.
  2. Write SE(3) and SO(3) helpers as Scaly templates: compose, inverse, and the log/exp retraction. The factor residuals should be identical to SymForce's.
  3. Write LM as a while_loop with the generated sparse LDLᵀ. Check that the iterates match SymForce to 1e-9.
  4. Scaling sweep: synthetic trajectories from 5 to 1000 poses. Report linearisation µs, iteration µs, source size and compile time against SymForce fixed and dynamic.
  5. Stretch: a small BAL instance17 (Ladybug-49) against Ceres with the Schur complement. Check whether AMD on the generated pattern recovers a Schur-like elimination order.

Success: a full iteration below SymForce fixed's time at 5 poses, and a gap that widens with graph size, with no compile blow-up.

E8 · 6-DoF powered-descent guidance by successive convexification

aerospace (outside control)L3 L1 L4effort Lneeds conic IPM

Papers and key computation

Each SCvx or PTR iteration has three steps:

  1. discretise the nonlinear dynamics, which means integrating the flow map and its state-transition and input sensitivities;
  2. solve a convex SOCP (thrust bounds, pointing, glide slope, trust region);
  3. update.

The baselines are:

  • Szmuk et al.18: ECOS through CVX with C++ propagation. Median 0.16–0.65 s per solve; propagation at most about 10 ms.
  • Reynolds et al.19: C++ with the custom BSOCP IPM. About 100 ms on one core, with only about 2% of the time outside the solver. The STM is integrated by RK4 as a flat augmented ODE of size nx(nx+2nu+3).
  • Malyuta et al.20: Julia with ECOS. Roughly 10–15 s cumulative for the 6-DoF free-flyer.
  • OpenSCvx21: JAX with CVXPY, Clarabel or QOCOGEN. It reports 1.6–2.1 s of initialisation (JIT), which "dominates the overall runtime", plus 0.05–0.13 s of solve.

Why Scaly should do better

  • The whole PTR loop becomes one generated C function (L3). The discretisation is the forward-mode Jacobian of an RK scan (L1), not an augmented ODE. The subproblem is a generated IPM on the fixed conic KKT pattern (L4).
  • Against OpenSCvx and the Julia/ECOS code, the gain should be large: no JIT, no modelling layer, no generic conic solver.
  • Against the C++/BSOCP baseline, which is bound by its solver, a win requires Scaly's generated IPM to handle second-order cones about as well as BSOCP or QOCOGEN.
  • Approximating the cones by polyhedra and passing them to PIQP changes the problem, and does not count as the comparison.

Implementation plan

  1. Phase A (no new features): reproduce an OpenSCvx 6-DoF landing or rocket example. Implement the same PTR in Scaly, with the subproblem solved by IPOPT treating each cone as a smooth convex constraint (‖·‖² ≤ r²).
    • Compare discretisation time directly: forward-mode through a scan against JAX with Diffrax.
    • Report setup time and total time.
  2. Phase B (feature): add second-order cones to the generated IPM. Nesterov–Todd scaling gives a KKT with a fixed block pattern, which the generated LDLᵀ handles unchanged. This belongs in the PIQP plan as its own tier, and it also unlocks the SOCP halves of E3 and of Conic-TinyMPC.
  3. Phase C: the full PTR as one C function. Compare it with OpenSCvx using CVXPYgen/QOCOGEN (the reproducible baseline) and with the published C++/BSOCP timings as context. The BSOCP code is not public.

Success: Phase A at least 10× faster than OpenSCvx end to end, setup included. Phase C inside Reynolds et al.'s ~100 ms class for the same node count on one core.
