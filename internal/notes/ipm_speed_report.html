Speeding up the generated PIQP

Where the generated solvers spend their time, what changed in the generated code, and the result · branch claude/ipm-speed (on claude/examples-tinympc-notebooks), todo C-135 … C-141 · 27 Sep 2026 · Apple M3 Max, Apple clang 21, the JIT's -O2 -mcpu=native -fno-math-errno

Summary. Six changes to the code generator and the IPM, plus a review round, over the 55 problems of the Tier 3 benchmark (48 Maros–Mészáros, 3 MPC, the 4 examples/qp_solvers families). Every time is the generated solver called from C (no Python), the fastest of five interleaved rounds against the base commit.

  • Sparse backend: 1.37× faster (geometric mean over 55; 1.51× over the 38 problems where PIQP's solve takes at least 50 µs). Against vendored PIQP 0.6.2's own warmed solve timer it goes from 1.19× to 0.78× on those 38, and is now faster than PIQP on 36 of them; 0.58× PIQP's setup + solve. Iteration counts and solutions are identical to the base on all 55.
  • Dense backend: 1.53× faster (1.76× above the 50 µs floor, up to 3.00×). Against PIQP's dense backend: 2.14× → 1.22×. The new Cholesky rounds differently: 2 of 55 problems change iteration count (QBEACONF 23 → 17, QBORE3D 19 → 21; PIQP's dense backend takes 23 and 20).
  • Side effects: generated objects 29% (sparse) and 21% (dense) smaller, compile time 13% and 9% shorter (the padded factorization tables are gone); graph build and generation unchanged.
  • Tests: 2 348 passed, 42 skipped; the one failure is the uncommitted tiny_qp gallery test in the working tree (the example has no main() yet). 51 mutants across the changes: 48 killed (several after a new test), 2 equivalent, 1 dead branch removed.

A look at the generated C behind those numbers:

  • Sparse factorization. One scan step per column, each running every column's groups padded to the widest row of its segment (22–65% of the slots real work), one read-modify-write of the work column per contributing column, and a separate padded clear. The sums of a supernode's columns into one row were done one column at a time.
  • Dense Cholesky. Crout, one entry at a time: two loads per multiply-add, about 3.3 G multiply-adds a second, a quarter of Eigen's blocked LLT in PIQP.
  • Step. About 200 loops of 100–400 elements per iteration. Every norm_inf, residual maximum and step-length minimum stored its vector before reducing it: the four-lane max/min reduction read its input from six statements, and producer fusion only inlines into one.
  • Loop carries. Every while loop copied its carry into its ping-pong store and back out after the loop, even the refinement loops that ran zero times with refinement off (about 3 600 values per solve), and the retry loop copied the whole factor record in and out on each factorization.

What the new ops cost in derivatives. Neither op differentiates in the factor: SparseLDL.solve's implicit rules never need it (dx = K⁻¹(db − dK x)), and schedule="scan" stays available, differentiable through its loops. So that the rules can hold a factor that refuses a tangent, forward mode now forms a call argument's tangent only if the callee's derivative reads it (single- and multi-seed), the map reverse rule drops constant-zero cotangents, and a call is differentiated only in the formals that depend on the variables. The one behavior change: third derivatives in the matrix, which reach the factorization itself, now need schedule="scan" above sparse_unroll; the guide says so and a test pins it.

Why the Cholesky keeps four partial sums. One running sum per tile entry was 2–5% faster, but it rounds worse on long dot products, and late in an interior-point solve the condensed matrix's last pivots are rounding noise: with it QSHARE1B failed a factorization at iteration 18 and took 56 iterations instead of 27 (PIQP: 29). Four contiguous quarters keep the old kernel's accuracy class; over the 55 problems only QBEACONF and QBORE3D change path, both problems on which PIQP's own two backends disagree. The strengthened decision gate now fails the single-sum variant.

Tried and not kept

  • Dense Cholesky variants. One running sum per tile entry (QSHARE1B, above); two interleaved sums (2.2× the old kernel against 3.3×: register pressure); partial sums over 64-column blocks (as fast as quarters, but a new rounding to validate for no gain); a transposed copy of L so the tile's column operands are contiguous (no gain: clang did not pair them into NEON FMAs).
  • 32-bit index tables for the factorization: 1–5% in the C prototype, not worth a second table type.
  • Dropping the second regularized pass and the final state selects of the step (C-134's suggestions): measured as 0–2%, within noise; the step's cost is spread over ~200 small loops, not in those.
  • Unscaling residuals by stored inverses, as PIQP does, instead of dividing each iteration: 0.99×, identical solutions; not worth two more loop params.
  • An output alias through reshapes (the dense factor written straight into the procedure's output): 4% faster below n = 111 but 7% slower on QSC205's dense backend; reverted.
  • -O3 instead of the JIT's -O2: 0.99–1.02× with Apple clang, confirming C-107's choice here.

Next levers

  • A dense Cholesky kernel closer to Eigen's. The tiles run scalar FMAs at 10–13 GFMA/s. A quick C prototype of the same 4×4 tile with explicit 2-wide NEON accumulators over a transposed copy of L gained only 1.07–1.11× at n = 230–300 (and lost at n = 111): eight vector accumulators do not hide the FMA latency. What Eigen does, larger register tiles (16 vector accumulators) over packed panels, would need vector values in the program dialect. This is the dense backend's remaining gap on dense P.
  • The backward sweep by chains. Only the forward sweep uses the chains; keeping the backward sweep's four partial sums per column bit for bit needs per-column lane alignment inside the shared loop.
  • The step's small loops. Two hundred loops of a few hundred elements; fusing producers read by two consumers (recomputing cheap ones) would take out a share of them.
  • Writing a call's output into the concatenation that consumes it (the factor into the retry record; the rest of C-131): 1–2% at n ≈ 100 dense.
  • QRECIPE (C-130) is now the one sparse problem far from PIQP, by iteration count, not speed.
