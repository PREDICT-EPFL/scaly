# Case study E6: AC optimal power flow (PGLib-OPF, JuMP, ExaModels)

The ExaModels paper's AC-OPF benchmark: PGLib-OPF cases solved by Ipopt through different modelling
layers. Here rosetta-opf's JuMP model and its ExaModels model run against the same model generated by
Scaly, all three through Ipopt 3.14.19 with MUMPS.

```bash
examples/case_studies/acopf/baseline/setup.sh     # rosetta-opf and pglib-opf pinned, Julia and the pinned environment
uv run examples/case_studies/acopf/compare.py --out examples/case_studies/acopf/results/sweep.json
uv run --with jupyterlab jupyter lab examples/case_studies/acopf/acopf.ipynb
```

`acopf.ipynb` explains the model, builds and solves two cases with Scaly without Julia, checks the
solution against a bus admittance matrix, and plots the recorded sweep. Its `RUN_BASELINES` flag reruns it.

## The model and the three stacks

rosetta-opf (lanl-ansi/rosetta-opf at `496d026`) states the AC-OPF as PowerModels' reference model does:

- variables: voltage angle and magnitude per bus, generation per generator, and the active and reactive
  flows at both ends of every branch;
- objective: the generators' quadratic costs;
- equalities: the reference angle, a power balance per bus, four flow equations per branch (pi model
  with tap ratio and phase shift);
- inequalities: the angle-difference window per branch and the thermal limit at both ends.

- **JuMP**: rosetta-opf's `jump.jl`, run unmodified (JuMP 1.31.2, Ipopt.jl 1.16.0).
- **ExaModels**: rosetta-opf's `examodels.jl`, written for ExaModels 0.7; `baseline/examodels_v0.12.patch`
  renames its calls to ExaModels 0.12's (`@add_var`, `@add_con`, `@add_con!`), the same model, so it
  runs against the same Ipopt build as the other two (NLPModelsIpopt 0.11.3).
- **Scaly**: `scaly_impl.py`, the same model term for term, every term written for all buses,
  generators or branches at once with `sc.gather` and `sc.segment_sum`; `sc.solver(problem, "ipopt")`.
  It reads the case as `baseline/export_case.jl` writes it: PowerModels' processing (per unit,
  corrected angle limits, quadratic costs, thermal limits) with every collection in JuMP's order.

Ipopt 3.14.19 (Ipopt_jll 300.1400.1902 on the Julia side, the version Scaly's plugin builds), MUMPS,
`tol` 1e-8 and 1e-4 (the paper's). The Julia side reads its options from an `ipopt.opt` in the working
directory, so the models' own code runs as published; Scaly gets the same values. Every process solves
the case twice and records the second solve (the Julia processes first solve rosetta-opf's warm-up
case). All three are timed by Ipopt's own timing statistics, parsed the same way.

"First solve" is a fresh process to the end of the first solve of the case, less interpreter start-up:
for Julia the package load, rosetta-opf's warm-up case (which compiles the model code) and the first
solve; for Scaly the import, the build, C generation and compile, and the first solve. At `tol` 1e-4
(`results/sweep.json`) every stack takes 2 to 3 fewer iterations and the comparison is the same.

- **The same solves.** The three stacks take the same Ipopt iterations on every case (JuMP one fewer
  on case13659, at both tolerances) and reach the same objective: Scaly's equals JuMP's to every printed
  digit, ExaModels' differs by about 1e-9 relative. The PGLib-OPF optima (five digits in its
  `BASELINE.md`) agree.
- **Function evaluations: Scaly is 10.6 to 10.7x below JuMP at case1354 and case2869 (6 to 8x on the
  small cases) and within 1.3x of ExaModels up to case1354**, the plan's criteria. From case2869 on it
  falls behind ExaModels: 1.7x at case2869, 4.4x at case9241 and case13659, where it is only 4.1x below
  JuMP. The cause is the Hessian (next section).
- **The whole solve: Scaly and ExaModels are level (Scaly 0.88 to 1.06x ExaModels' time), both 1.4 to
  2x faster than JuMP.** With ExaModels, Ipopt's linear algebra is 77 to 88% of the solve, so beating it
  on CPU would need a faster KKT solve, as the plan expected.
- **Time to a first solution: Scaly is fastest up to case2869** (1.5 to 8.9 s against JuMP's 4.7 to
  10.5 and ExaModels' 9.7 to 13.0) and **slowest at case9241 and case13659** (53 and 66 s against 24
  and 29 for ExaModels). The plan's "setup below 5 s up to 10k buses" holds to case1354 only.

## Why Scaly's derivatives and setup grow faster than the network

Scaly evaluates the Lagrangian Hessian and the constraint Jacobian by colouring: one forward-over-reverse
(or forward) sweep of the whole model per colour. The colour width tracks the largest bus degree, which
grows with the network:

| Case | Variables | Hessian colours | Jacobian colours | Generated C |
|---|---:|---:|---:|---:|
| case118_ieee | 1,088 | 12 | 15 | |
| case1354_pegase | 11,192 | 18 | 21 | 13.8 MB |
| case2869_pegase | 25,086 | 28 | 21 | |
| case9241_pegase | 85,568 | 74 | 48 | 277 MB |

Evaluation and code both grow as variables x colours. At case9241 the Hessian takes 1.28 s per solve
against ExaModels' 0.23 s, and the 277 MB of C take 12 s to render and 22 s to compile. ExaModels forms
each constraint pattern's small local Hessian and scatters it into the sparse result, which grows with
the number of nonzeros. Doing the same for Scaly's gathered and `vmap`ped patterns is CS-5 in
`internal/todo.md`. The colouring algorithm itself scales: `sc.solver` builds case13659's problem,
sparsity and colouring in 3.7 s.

## Files

| File | What it is |
| --- | --- |
| `baseline/setup.sh` | pins rosetta-opf (`496d026`) and pglib-opf (v23.07), Julia 1.10.12 and `baseline/julia_env` |
| `baseline/export_case.jl` | a case as PowerModels processes it for rosetta-opf, in JuMP's order, as JSON |
| `baseline/run_rosetta.jl` | one rosetta-opf model on one case: the warm-up, then two solves |
| `baseline/examodels_v0.12.patch` | rosetta-opf's ExaModels model in ExaModels 0.12's names |
| `scaly_impl.py` | the model in Scaly, and the reader of the exported case |
| `run_scaly.py` | one case with Scaly: build, compile, two solves |
| `compare.py` | the sweep: cases x tolerances x stacks, fresh processes, Ipopt's timing statistics |
| `results/cases/` | case14 and case118 as exported, for the notebook (CC BY 4.0, see its README) |
| `acopf.ipynb` | the study as a notebook |

`tests/integration/test_case_study_acopf.py` builds the same model for a 3-bus network with a
phase-shifting transformer and a shunt, and checks Scaly's solution against a bus admittance matrix and
against SciPy's SLSQP on the problem written with that matrix.

Not done: MadNLP (the paper's solver for ExaModels; here every stack uses Ipopt, so the comparison
is of the modelling layers), MA27 (no HSL licence here; MUMPS on every side), the GPU column, the 24-period
extension, and case30000 (the colour width would grow further).
